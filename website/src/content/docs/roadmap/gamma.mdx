AutoBE Gamma 로드맵은 [v1.0 legacy roadmap](./v1.0-legacy)에서 전략적으로 전환된 계획이다. Enterprise Development 단계에서의 실제 필드 테스트를 통해 얻은 교훈을 바탕으로, 보다 실용적이고 빠른 개발 방향으로 로드맵을 재편성하였다.

**전략적 변화**: v1.0 로드맵이 각 기능의 100% 완성도(컴파일 성공률 100%, 런타임 성공률 100%)를 추구했다면, Gamma 릴리즈는 개발 주기를 대폭 단축하고 더 많은 기능을 포괄하되, 각 티켓마다 기초 설계와 프로토타입 구현에 집중한다. 완벽함보다는 실질적인 가치 전달을 우선시하며, 이후 단계에서 품질 개선을 진행하는 방식이다.

**팀 확장 계획**: Gamma에서 구축한 핵심 기능들은 세분화된 티켓으로 나뉘어, 새롭게 채용할 AutoBE 개발자들이 품질 강화와 프로덕션 안정화를 담당한다. 이러한 병렬 개발 전략을 통해 속도와 품질 양쪽을 모두 확보한다.

## 1. Production Testing
### 1.1. Hackathon Contest
AutoBE의 기반 프레임워크인 Agentica를 주제로 오픈소스 해커톤 대회를 공동 개최하였다. 참여자들은 AutoBE를 활용하여 백엔드 어플리케이션을 생성하고 리뷰하며 다양한 피드백을 제공하였다.

**주요 관찰 사항**:
- 참가자들은 자연어 인터페이스를 통해 완전한 백엔드 어플리케이션 생성에 성공하였다
- 상금이 걸린 경쟁 환경 특성상, 비판적 시각의 피드백은 제한적이었다
- 생성된 코드베이스가 방대한 규모(10만 줄 이상)여서, 사람이 직접 꼼꼼히 검토하기보다 AI의 도움을 받아 평가 보고서를 작성하는 경우가 많았다

**교훈**: 해커톤을 통해 AutoBE의 코드 생성 능력은 검증되었으나, 보다 현실적인 개발 환경에서 심도 있는 비판적 평가가 필요함을 인식하게 되었다.

### 1.2. Open Source Contest
한국 정부와 공동으로 Agentica 오픈소스 대회를 개최하였다.

**Agentica의 역할**: Agentica는 function calling에 특화된 Agentic AI 프레임워크로서, AutoBE의 핵심 엔진 역할을 수행한다. 특히 [`AutoBePrisma.IApplication`](https://github.com/wrtnlabs/autobe/blob/main/packages/interface/src/prisma/AutoBePrisma.ts), [`AutoBeOpenApi.IDocument`](https://github.com/wrtnlabs/autobe/blob/main/packages/interface/src/openapi/AutoBeOpenApi.ts), [`AutoBeTest.IFunction`](https://github.com/wrtnlabs/autobe/blob/main/packages/interface/src/test/AutoBeTest.ts) 등 컴파일러 AST 구조를 function calling으로 생성하고, 타입 오류를 자동으로 교정하는데 핵심적인 기능을 담당한다.

**대회 성과**:
- Agentica를 활용한 AI 챗봇 및 에이전트 어플리케이션 개발 대회로 진행
- 다수의 팀이 참가하였으며, 본선에 총 10개 팀이 진출하여 경쟁 중
- 실제 활용 사례와 피드백을 수집하며, Agentica의 발전 방향 모색
- Function calling을 위한 스키마 설계와 에이전트 활용에 뛰어난 역량을 보인 참가자들을 Wrtn Technologies AX 개발팀으로 추천 예정

**전략적 가치**: 대회를 통해 피드백을 수집할 뿐만 아니라, 스키마 설계 및 function calling 아키텍처에 전문성을 가진 인재를 발굴하는 인재 파이프라인으로도 기능한다.

### 1.3. Enterprise Development
Wrtn Technologies의 B2B 엔터프라이즈 백엔드를 AutoBE로 구축하고, 실제 운영 환경에 약 한 달 간 배포하여 엔터프라이즈 규모의 첫 실전 검증을 수행하였다.

**배경**: Wrtn Technologies는 월 활성 사용자(MAU) 700만 명을 보유한 대규모 AI 챗봇 서비스([https://wrtn.ai](https://wrtn.ai))를 운영 중이다. 기존 B2C 서비스를 B2B 시장으로 확장하면서, AutoBE를 활용한 백엔드 개발로 플랫폼의 실전 역량을 시험하였다.

**핵심 인사이트**: 엔터프라이즈 환경에서 AutoBE를 운영하며, 강점과 동시에 명확한 한계점을 발견하였다. 이러한 현장 경험이 Gamma 로드맵의 방향성을 결정하는 결정적 계기가 되었다.

**도출된 핵심 요구사항**:

1. **스펙 직접 지시**: DB 설계나 API 스펙에 대해 자연어가 아닌 직접적인 기술 명세 제공 기능
2. **DTO 보안 강화**: Interface phase의 DTO 설계에서 데이터 무결성, 안전성, 보안성 대폭 강화
3. **이미지 기반 요구사항 분석**: Figma 등 시각적 산출물로부터 요구사항 자동 추출
4. **RAG 최적화**: 하위 기능들을 지원하기 위한 토큰 효율화 및 선택적 컨텍스트 로딩
5. **코드 모듈화**: Test 및 Realize agent가 재사용 가능한 모듈 코드를 생성하여 개발자의 수정 편의성 향상
6. **유지보수 기능**: 생성된 백엔드를 점진적으로 개선할 수 있는 incrementa update 기능

**영향**: 이 한 달간의 실전 경험이 수개월의 이론적 기획보다 더 가치 있는 통찰을 제공하였으며, Gamma 릴리즈 계획 수립의 직접적 근거가 되었다.

### 1.4. Performance Benchmark
AutoBE의 운영 효율성을 다차원적으로 측정, 평가, 최적화하는 종합 성능 벤치마크 시스템을 구축한다.

**측정 지표**:
- **생성 속도**: 각 파이프라인 단계(Requirements → Analyze → Prisma → Interface → Test → Realize) 완료 시간
- **토큰 효율성**: 작업당 토큰 소비량, 특히 RAG 최적화 시 개선 효과 측정
- **컴파일 성공률**: 생성된 코드가 TypeScript, OpenAPI, Prisma 컴파일러 검증을 1회 시도에 통과하는 비율
- **런타임 성공률**: 생성된 백엔드의 E2E 테스트 통과율(사람 개입 없이)
- **품질 지표**: 코드 유지보수성, 테스트 커버리지, 모범 사례 준수도

**지속적 개선 루프**: 벤치마크 데이터는 에이전트 시스템 프롬프트 개선 및 오케스트레이션 최적화에 직접 반영된다. 성능 저하 발생 시 즉시 조사하고, 개선 사항은 아키텍처 결정의 검증 지표로 활용한다.

**전략적 가치**: Gamma 기간 동안 기능 확장을 진행하면서도, 체계적인 성능 모니터링을 통해 새로운 기능이 사용자 경험을 향상시키는지 악화시키는지 객관적으로 판단할 수 있다.

## 2. Lessons Learned
### 2.1. Direct Instruction
정밀한 기술 명세가 필요한 상황에서, 사용자가 DB 스키마나 API 스펙을 자연어가 아닌 직접적 지시로 제공할 수 있어야 한다.

**자연어의 한계**: AutoBE는 자연어 인터페이스를 통한 백엔드 생성을 핵심 가치로 삼아왔다. 그러나 엔터프라이즈 필드 테스트 결과, 직접 명세가 필수적인 상황들이 존재함을 확인하였다:
- 기존 시스템과 공유하는 테이블 스키마 (예: AI 챗봇 대화 테이블)
- B2B 통합을 위한 필수 API 규격 및 형식
- 규제 준수를 위해 정확히 정의되어야 하는 데이터 구조
- 레거시 시스템 호환성 제약사항

**현재 아키텍처의 간극**: AutoBE는 사용자 대화에서 요구사항을 추출하여 Analyze agent에만 전달한다. Prisma (DB 설계) 및 Interface (API 설계) agent는 Analyze의 출력만 받을 뿐, 사용자의 직접적인 기술 명세를 수신할 수 없다.

**Gamma 개선**: 명세 추출 시스템을 구현하여:
1. 사용자 대화에서 직접적 기술 지시를 파싱
2. 자연어 요구사항은 Analyze agent로 라우팅 (기존 방식 유지)
3. DB/API 명세는 Prisma 및 Interface agent에 직접 전달
4. 사용자가 고수준 의도와 저수준 기술 제약을 동시에 명시할 수 있는 하이브리드 워크플로우 지원

**영향**: 접근성은 유지하면서도, 비즈니스 맥락상 필수적인 아키텍처 결정을 사용자가 직접 통제할 수 있는 권한을 부여한다.

### 2.2. Interface Schema Review
Interface phase의 DTO 설계 프로세스를 전문화된 리뷰 에이전트로 분할하여, 관계 무결성, 보안 강화, 내용 완전성 각 영역을 심층적으로 검증할 계획이다.

**개발 배경**: 현재 단일 Review Agent가 DTO 설계에 대한 검증 일체를 담당하고 있다. 엔터프라이즈 필드 테스트 결과, 이 모놀리식 접근법이 관계 모델링, 보안 제약, 내용 정확성이라는 서로 경쟁하는 요구사항을 동시에 다루는데 한계가 있음이 드러났다. Gamma에서는 3단계 리뷰 파이프라인을 구축할 예정이다:

**1. Relation Review Agent**
- 외래 키 관계 및 중첩 객체 구조 검증
- DTO 변형(Create, Update, Read)이 엔티티 연관관계를 올바르게 표현하는지 확인
  - composition
  - aggregation
  - association
- Prisma 모델과 OpenAPI 스키마 간 관계 불일치 탐지 및 교정
- 복잡한 시나리오 처리: 선택적/필수 관계, 계단식 갱신, 순환 의존성

**2. Security Review Agent**
- 클라이언트 제공 데이터와 서버 관리 데이터 간 인증 경계 분리 강제
- 요청 DTO에 해시된 비밀번호 필드 노출 등 치명적 취약점 방지
- 인증된 요청 본문에서 actor identity 필드(예: `user_id`, `member_id`) 제거 검증
- 응답 DTO가 민감한 시스템 필드(토큰, 솔트, 내부 ID) 유출하지 않도록 보장

**3. Content Review Agent**
- Prisma 스키마와 교차 참조하여 필드 완전성 보장
- 데이터 타입 매핑(Prisma → OpenAPI JSON Schema) 검증
- 비즈니스 로직 기반 필수/선택 필드 설정 강제
- 모든 속성에 대한 종합적 문서화 보장

**기대 효과**: 관심사 분리를 통해 각 에이전트가 해당 영역을 심층 전문화할 수 있게 되어, DTO 품질이 극적으로 향상될 것이다. 현재 누락되는 보안 취약점을 체계적으로 포착하고, 관계 모델링 오류를 코드 생성 전에 탐지하며, 필드 완전성을 자동 교차 참조를 통해 보장할 수 있을 것으로 기대한다.

### 2.3. JSON Schema Guideline
Interface 스키마 리뷰 에이전트를 정교하게 전문화할 계획인데, 이에 따라 예상되는 도전과제가 있다: 많은 LLM 모델들이 구문적으로 유효하고 의미적으로 올바른 JSON Schema 구조를 일관되게 생성하는데 어려움을 겪는다.

**예상되는 오픈소스 모델의 도전과제**: GPT-4.1 같은 상용 모델은 JSON Schema 생성을 안정적으로 처리하지만, 오픈소스 대안들은 빈번하게 잘못된 스키마를 생성할 가능성이 있다. 특히 3단계 리뷰 파이프라인을 도입하면 이 문제가 증폭될 수 있다—관계, 보안, 내용 리뷰 에이전트가 상호 의존적 수정을 가할 때, 사소한 JSON Schema 오류조차도 컴파일 실패로 연쇄적으로 확대될 수 있다.

**근본 원인 분석**: LLM은 JSON Schema의 미묘한 요구사항에 대한 명시적 구조 가이드가 부족하다:
- `properties`, `required`, `additionalProperties`의 올바른 중첩
- 스키마 컴포지션을 위한 `$ref`의 정확한 사용
- 유효한 `type` 제약 및 형식 지정자
- 검증 키워드(`minLength`, `pattern`, `enum` 등)의 적절한 적용
- OpenAPI 전용 확장과 핵심 JSON Schema의 구분

**계획된 해결책: 규범적 가이드라인**: Gamma에서는 에이전트 시스템 프롬프트에 직접 내장되는 포괄적 JSON Schema 작성 가이드라인을 개발할 예정이다:
1. **구조 템플릿**: 일반적인 DTO 시나리오(Create, Update, Read 변형)에 대한 사전 검증된 패턴
2. **제약 명세**: 특정 검증 키워드를 언제 사용할지에 대한 명확한 규칙
3. **참조 패턴**: 엔티티 관계 및 중첩 객체를 위한 표준 접근법
4. **안티 패턴**: 일반적 실수와 그 교정 방법에 대한 명시적 문서화

**기대 효과**: 에이전트에게 명확하고 규범적인 JSON Schema 구성 규칙을 제공함으로써, 역량이 떨어지는 모델에서도 잘못된 스키마 생성을 극적으로 감소시킬 수 있을 것으로 기대한다. 이는 AutoBE의 모델 호환성을 확대하여, 생성 품질을 유지하면서도 운영 비용을 절감할 수 있을 것이다.

### 2.4. Image Understanding
요구사항은 깔끔한 텍스트 문서로 도착하지 않는다. 실제 소프트웨어 개발은 Figma 목업, 화이트보드 다이어그램, 주석이 달린 와이어프레임의 혼란스러운 교차점에서 작동한다. AutoBE는 대화뿐만 아니라 시각적 산출물로부터도 요구사항을 추출하고 해석할 수 있어야 한다.

**시각적 요구사항의 현실**: 엔터프라이즈 필드 테스트 동안, 핵심 요구사항이 디자인 파일에만 존재하는 경우를 빈번하게 발견하였다:
- **Figma 디자인**: UI 레이아웃이 암묵적으로 데이터 모델 정의 (예: 폼 필드 = DTO 속성)
- **와이어프레임**: 네비게이션 흐름이 API 엔드포인트 구조 노출
- **ERD 다이어그램**: 손으로 그렸거나 도구로 생성된 데이터베이스 스키마
- **플로우차트**: 특정 API 작업이 필요한 비즈니스 로직 시퀀스
- **스크린샷**: 마이그레이션 명세를 제공하는 기존 시스템

Wrtn Technologies 내부에서조차, 공식 요구사항 문서는 불완전한 경우가 많았고, "진실의 원천"은 명세 문서가 아닌 디자인 산출물에 존재하였다.

**개발 계획: 멀티모달 분석 파이프라인**: Gamma에서는 시각 이해 능력을 가진 에이전트를 개발할 예정이다:
1. **구조 정보 추출**: 시각적 레이아웃을 파싱하여 데이터 모델 및 엔티티 관계 추론
2. **암묵적 요구사항 식별**: 디자인 결정에 내재된 요구사항 탐지 (예: 페이지네이션 컨트롤 = 오프셋 기반 API 설계 암시)
3. **텍스트와 교차 참조**: 이미지 분석을 대화 컨텍스트와 결합하여 종합적 이해
4. **구조화된 요구사항 생성**: 시각적 입력으로부터 공식 요구사항 명세 생산

**Analyze Agent와의 통합 계획**: 이미지로부터 파생된 요구사항을 기존 Analyze agent 파이프라인으로 전달하여, 텍스트 요구사항과 병합하여 전체론적 분석을 수행하도록 구현할 예정이다. 이 멀티모달 접근을 통해 제품 팀이 실제로 의도를 전달하는 전체 스펙트럼을 포착할 수 있을 것이다.

**장기 비전**: 멀티모달 LLM 능력이 발전함에 따라, AutoBE는 시각적 이해에 점점 더 의존하게 될 것이며, 최종적으로는 Figma 링크나 스크린샷 업로드를 주요 요구사항 소스로 수용하는 것을 목표로 한다.

## 3. RAG Optimization

지능형 순환 워크플로우를 통해 토큰 효율성을 극대화하고 생성 품질을 향상시키는 차세대 아키텍처로 전환한다.

**현재의 한계**: AutoBE의 각 에이전트는 현재 상류 산출물을 한꺼번에 받는 단일 모놀리식 function call로 작동한다:
- **Test Agent**는 모든 문서, 모든 Prisma 모델, 모든 API 작업을 동시에 수신
- **Realize Agent**는 완전한 OpenAPI 명세와 모든 테스트 시나리오를 한번에 수집
- 프로젝트 복잡도에 따라 토큰 소비가 기하급수적으로 증가
- 에이전트가 특정 컴포넌트를 선택적으로 탐색하거나 반복할 수 없음

이 "일괄 처리" 접근은 초기 검증에는 효과적이었으나, 다음 기능들에 극복 불가능한 장벽을 만든다:
- **모듈화**: 선택적 컨텍스트 없이는 에이전트가 코드 모듈 간 관계를 분석할 수 없음
- **유지보수/보완**: 점진적 업데이트가 전체 컨텍스트 재생성 필요
- **엔터프라이즈 규모**: 대규모 프로젝트가 컨텍스트 윈도우 한계 초과

**RAG 혁명**: Gamma는 에이전트가 **필요한 정보만 능동적으로 쿼리하고 선택적으로 로드**하는 순환형, 검색 증강 생성 워크플로우를 도입한다. 에이전트는 수동적 소비자가 아닌 능동적 탐색자가 된다.

**에이전트 탐색 방법**:
1. **초기 평가**: 사용 가능한 산출물 검토 (파일 목록, 모델 이름, API 엔드포인트)
2. **선택적 검색**: 현재 작업에 기반하여 특정 문서, 모델, 작업 요청
3. **반복적 정제**: 필요에 따라 추가 컨텍스트 로드, 필요 이상으로는 절대 로드하지 않음
4. **완료**: 충분한 정보가 수집되면 출력 생성

**혁신적 개선 효과**:
- **70% 토큰 소비 절감**: 선택적 정보 로딩을 통한 불필요한 컨텍스트 제거
- **메모리 효율성 향상**: 대규모 프로젝트에서도 안정적인 처리
- **정확도 향상**: 집중된 컨텍스트로 더욱 정확한 코드 생성
- **점진적 개선**: 각 단계에서 피드백 즉시 반영
- **모듈화 가능**: 에이전트가 코드 구조를 분석하고, 공통 패턴을 식별하며, 재사용 가능한 모듈 추출 (§4)
- **유지보수 지원**: 점진적 업데이트가 영향받는 컴포넌트만 로드 (§5)
- **엔터프라이즈 확장성**: 프로젝트 크기에 따른 선형적 토큰 증가 (기하급수적이 아님)

이 순환형 워크플로우는 AutoBE를 더욱 스마트하고 효율적인 시스템으로 진화시켜, 대규모 엔터프라이즈 프로젝트에서도 비용 효율적인 운영을 가능하게 한다.

**핵심 의존성**: RAG 최적화는 단순한 성능 개선이 아니라, 모듈화(§4)와 보완(§5)의 아키텍처 전제조건이다. 선택적 컨텍스트 로딩 없이는 에이전트가 코드 관계를 추론하거나 타겟팅된 업데이트를 수행할 수 없다.

## 4. Modularization
실제 개발자들은 생성된 코드를 수정해야 한다. 엔터프라이즈 필드 테스트 결과, AutoBE의 현재 출력물은 기능적으로는 정확하지만, 테스트 및 구현 파일 전반에 걸친 광범위한 코드 중복으로 인해 사람의 유지보수에 구조적으로 적대적임이 드러났다.

**유지보수 문제**: B2B 백엔드 개발 중, 개발자들은 생성된 코드를 자주 커스터마이징해야 했다:
- 회사 고유의 보안 정책 통합
- 제3자 결제 게이트웨이 커넥터 추가
- 기존 AI 챗봇 시스템과의 인터페이스
- WebSocket 스트리밍 기능 구현
- 조직 전체의 에러 처리 규칙 적용

**현재 아키텍처의 약점**: AutoBE는 컴파일 및 런타임 성공률(100% 목표)을 우선시하여 에이전트가 자체 완결형 독립 구현을 생성하도록 했다:
- **Test Agent**: 각 E2E 테스트 함수에 인라인 인증, 데이터 생성, 검증 로직 포함
- **Realize Agent**: 각 API 엔드포인트가 변환 및 데이터베이스 작업을 처음부터 구현

이 "복사-붙여넣기" 패턴은 정확성을 보장했으나 **유지보수 악몽**을 만들었다:
- 테스트 파일 전반에 걸쳐 수백 개의 중복된 인증 흐름
- 수십 개의 테스트 함수에 산재된 동일한 데이터 생성 로직
- 모든 API 핸들러에 중복된 Prisma-to-DTO 변환 코드
- 버그 수정을 위해 수많은 위치에서 수동 업데이트 필요

**전략적 지연의 근거**: 이는 실수가 아니라 의도적이었다. AutoBE의 초기 개발은 코드 우아함을 추구하기 전에 기능적 정확성을 입증하는 것을 올바르게 우선시했다. 모듈화는 성공적인 구현 전반의 패턴 이해가 필요하며, 이는 광범위한 생성 테스트 이후에만 나타났다.

**Gamma 모듈화 이니셔티브**: RAG 최적화가 선택적 코드 분석을 가능하게 하면(§3), 에이전트가 다음을 수행할 수 있도록 개발할 계획이다:
1. **패턴 감지**: 생성된 코드를 분석하여 공통 작업 식별
2. **모듈 추출**: 재사용 가능한 유틸리티 함수 및 클래스 생성
3. **구현 리팩토링**: 중복 코드를 모듈 호출로 대체
4. **정확성 유지**: 100% 컴파일 및 런타임 성공률 보존

### 4.1. (Test) Authorization
사용자 컨텍스트가 필요한 모든 테스트 함수에 반복되는 인증 및 권한 부여 로직을 모듈화할 예정이다.

인증 로직을 중앙화하여 전역 커스터마이징(예: JWT에서 세션 기반 인증으로 전환)을 단일 지점 수정으로 가능하게 할 것이다. 모든 테스트에서 인증 관련 수정 사항이 자동으로 반영되어, 일관성을 유지하면서도 유지보수 부담을 극적으로 감소시킬 수 있을 것으로 기대한다.

### 4.2. (Test) Data Creation
테스트 픽스처 설정을 위한 Create 엔드포인트 API 호출을 모듈화할 계획이다.

픽스처 생성을 일관되고 유지보수 가능하게 만들 것이다. DTO에 필수 필드를 추가할 때 팩토리 함수만 업데이트하면 되며, 모든 테스트가 자동으로 새 요구사항을 준수하게 된다. 또한 테스트 데이터 생성 로직을 중앙화하여 다양한 테스트 시나리오를 쉽게 지원할 수 있도록 할 것이다.

### 4.3. (Realize) Transformation
모든 GET 엔드포인트에 중복된 Prisma 모델에서 Read DTO로의 변환 로직을 모듈화할 예정이다.

계산된 필드 추가, 데이터 정제 적용, DTO 구조 조정을 한 곳에서만 변경할 수 있도록 할 것이다. 커스텀 비즈니스 로직(예: 민감 필드 편집)이 모든 엔드포인트에 일관되게 적용되도록 하며, 타입 안전성을 유지하면서도 변환 로직을 재사용할 수 있도록 개발하여, 코드 중복을 제거하고 유지보수성을 크게 향상시킬 계획이다.

### 4.4. (Realize) Collection
Create DTO에서 Prisma 입력 준비 로직을 모듈화하여, 중첩 관계 및 데이터 검증을 처리하도록 개발할 예정이다.

관계 처리 로직(connect, create, disconnect)을 재사용 가능한 모듈로 중앙화할 것이다. 조직별 데이터 변환이나 커스텀 검증을 추가하는 것을 간단하게 만들며, POST/PUT 엔드포인트 전반에 걸친 일관된 데이터 준비 패턴을 제공하고, DB 저장 직전 단계까지의 코드를 모듈화하여 유연성과 재사용성을 확보할 계획이다.

---

**모듈화 성공 기준**: 개발자가 수백 개의 생성된 파일을 뒤지는 대신, 유틸리티 모듈을 편집하여 횡단 관심사(인증, 로깅, 에러 처리, 데이터 변환)를 수정할 수 있어야 한다. 이는 AutoBE의 출력을 "정확하지만 유지보수 불가능"에서 "정확하면서 개발자 친화적"으로 변화시킨다.

## 5. Complementation
필드 테스트에서 가장 치명적으로 누락된 기능: 처음부터 재생성하는 대신 생성된 백엔드를 점진적으로 개선할 수 있는 능력. 사람은 10만 줄 이상의 코드를 한 번에 완벽하게 리뷰할 수 없다.

**완전 재생성의 문제**: 엔터프라이즈 필드 테스트 동안, 발견된 모든 문제가 전체 재생성 주기를 촉발하였다:
1. 개발자가 생성된 백엔드를 검토하고, 문제 식별 (불완전한 API, 잘못된 DTO, 누락된 검증)
2. 개발자가 AutoBE에 채팅으로 피드백 제공
3. AutoBE가 **전체 백엔드**를 처음부터 재생성
4. 개발자가 다시 검토하고, 이전에 놓쳤던 **새로운 문제** 발견 (코드가 너무 방대하여 완전한 검토 불가능)
5. 주기 반복...

이 재생성 루프는 프로덕션에서 AutoBE를 사용하는 데 있어 가장 좌절스러운 측면이었다. 주요 고통 포인트:
- **검토 피로**: 방대한 코드베이스를 반복적으로 종합적으로 검토하는 것은 불가능
- **점진적 발견**: 개발자가 다양한 영역을 탐색하면서 문제가 점진적으로 드러남
- **시간 낭비**: 문제 섹션과 함께 정확한 코드를 재생성
- **컨텍스트 손실**: 생성 간 변경 사항 추적 어려움

**왜 사람은 모든 것을 검토할 수 없는가**: 일반적인 AutoBE 생성 백엔드는 다음을 포함한다:
- 수십 개 파일에 걸친 50개 이상의 API 엔드포인트
- 복잡한 관계를 가진 Prisma 스키마
- 수백 개의 테스트 시나리오
- 수천 개의 TypeScript 타입 정의

완벽한 첫 번째 검토를 기대하는 것은 비현실적이다. 개발자는 전부 아니면 전무의 재생성이 아닌 **반복적 개선**이 필요하다.

**Gamma 보완 시스템 개발 계획**: RAG 최적화(§3)를 활용하여, AutoBE가 모든 파이프라인 단계에서 타겟팅된 유지보수 기능을 제공하도록 개발할 예정이다:

**Analyze Phase 보완** (개발 예정):
- 피드백 기반으로 특정 요구사항 문서 업데이트
- 누락된 사용자 스토리나 비즈니스 규칙 추가
- 전체 분석 재생성 없이 기존 요구사항 정제

**Prisma Phase 보완** (개발 예정):
- 특정 모델 수정 (필드 추가, 관계 조정, 제약 변경)
- 마이그레이션 스크립트 점진적 업데이트
- 수동으로 커스터마이징된 데이터베이스 로직 보존

**Interface Phase 보완** (개발 예정):
- 개별 DTO 정제 (검증 추가, 필드 타입 조정, 보안 문제 수정)
- 전체 OpenAPI 명세 재생성 없이 특정 API 작업 업데이트
- 스키마 업데이트 시 커스텀 엔드포인트 로직 유지

**Test Phase 보완** (개발 예정):
- 특정 엔드포인트를 위한 누락된 테스트 시나리오 추가
- 전체 테스트 스위트 재생성 없이 실패 테스트 업데이트
- 커스텀 테스트 유틸리티 및 픽스처 통합

**Realize Phase 보완** (개발 예정):
- 개별 API 구현 수정
- 특정 엔드포인트의 비즈니스 로직 업데이트
- 수동으로 추가한 통합 보존 (결제 게이트웨이, 외부 API, WebSocket 핸들러)

**기술적 기반**: RAG 최적화(§3)를 통해 다음이 가능하도록 구현할 계획이다:
1. **영향받는 컴포넌트 식별**: 업데이트가 필요한 모델/DTO/엔드포인트 결정
2. **선택적 컨텍스트 로드**: 관련 기존 코드 및 명세만 검색
3. **타겟팅된 변경 생성**: 완전한 재작성이 아닌 최소 diff 생산
4. **일관성 검증**: 변경 사항이 의존성을 깨지 않도록 보장

**성공 기준**: 개발자가 특정 변경("User.ICreate에 이메일 검증 추가", "Article 모델에 view_count 추가")을 요청하면, 관련 컴포넌트만 영향을 미치는 수술적 업데이트를 제공할 수 있어야 한다. "모두 불태우고 처음부터"의 시대를 종식시키는 것이 목표다.

## 6. Recruitment
AutoBE의 가속화된 개발 속도는 팀 확장을 요구한다. Gamma 프로토타입을 프로덕션 수준의 기능으로 변환할 전담 AutoBE 개발자를 채용한다.

**Gamma의 전략적 전환**: v1.0 로드맵이 다음 단계로 진행하기 전에 각 기능의 100% 컴파일 및 런타임 성공을 달성하는 데 집중한 반면, Gamma는 다음을 우선시한다:
- **완벽함보다 폭**: 더 많은 기능에 걸쳐 기초 구현 제공
- **프로토타입 우선 개발**: 핵심 아키텍처 및 워크플로우를 신속히 구축
- **의도적 기술 부채**: 더 빠른 검증을 위한 초기 품질 트레이드오프 수용
- **Gamma 이후 정제**: 이후 주기를 강화 및 최적화에 할애

**왜 이 접근법인가?**: 엔터프라이즈 필드 테스트는 이론적 완벽함보다 **개발자 경험과 실용적 유용성**이 더 중요하다고 가르쳤다. 사용자는 다음으로부터 더 많은 이득을 얻는다:
- 점진적 업데이트 기능 (초기에 불안정하더라도)
- 코드 모듈화 (패턴이 최적이 아니더라도)
- 직접 명세 제어 (에러 처리가 불완전하더라도)

모든 변경에 대해 전체 재생성이 필요한 완벽하게 컴파일되는 시스템보다.

**신규 개발자의 역할**: Gamma는 아키텍처 기반—RAG 인프라, 모듈화 패턴, 보완 워크플로우, 멀티모달 요구사항 처리—을 구축한다. 채용된 AutoBE 개발자는:
1. **프로토타입 분해**: Gamma 구현을 세분화된 개선 티켓으로 분할
2. **품질 강화**: 프로덕션급 안정성, 에러 처리, 엣지 케이스 커버리지 달성
3. **성능 최적화**: 프롬프트 엔지니어링, 캐싱 전략, 오케스트레이션 효율성 정제
4. **커버리지 확대**: Gamma 사용 중 발견된 롱테일 시나리오 해결
5. **모멘텀 유지**: Gamma 이후 지속적인 기능 개발 가능

**채용 타임라인**: Gamma 개발과 병행 진행 (§1 타임라인 참조). 기초 시스템을 구축하면서 동시에 이를 정제할 개발자를 온보딩한다. 이 중복은 Gamma 프로토타입이 완성되는 즉시 생산성을 보장한다.

**이상적인 후보자**: 다음을 갖춘 개발자를 찾는다:
- 깊이 있는 TypeScript/NestJS/Prisma 전문 지식
- LLM 능력과 한계에 대한 이해
- Function calling 및 에이전트 AI 시스템 경험 (Agentica 배경 이상적)
- 개발자 도구 및 코드 생성에 대한 열정
- 빠른 반복 및 프로토타입 정제에 대한 편안함

**Gamma 이후 비전**: 확장된 팀 역량으로, AutoBE는 창업자 주도 프로토타입 개발에서 지속 가능한 커뮤니티 주도 진화로 전환한다. Gamma 로드맵은 끝이 아니라 AutoBE의 다음 장을 위한 기반이다.
