## 1. Preface

6.75%.

쇼핑몰 백엔드의 API 데이터 타입을 `qwen3-coder-next`에게 맡기면, 첫 시도에서 유효한 결과가 나올 확률입니다. 100번 중 93번이 실패합니다.

[AutoBe](https://github.com/wrtnlabs/autobe)라는 오픈소스 AI 에이전트가 있습니다. 자연어 대화 한 번이면 요구사항 분석, 데이터베이스, API 명세, E2E 테스트, 구현 코드까지 전부 만들어냅니다. 여기에 방금 그 6.75% 모델을 물리면? 최종 컴파일 성공률 **100%**. Qwen 모델 4종 전부.

비결은 더 좋은 모델도, 더 똑똑한 프롬프트도 아닙니다. **하네스(harness)**입니다. 타입 스키마로 출력을 제약하고, 컴파일러로 결과를 검증하고, 틀리면 어디서 왜 틀렸는지 구조화된 피드백으로 짚어주고, LLM이 그걸 보고 스스로 교정합니다. 수렴할 때까지 반복합니다.

확률적 모델을 감싸는 결정론적 루프 — 모델 안이 아니라, 모델 바깥의 엔지니어링이 성패를 갈랐습니다.

이 발표는 그 엔지니어링을 해부합니다.

**2장**에서 AutoBe의 아키텍처를 봅니다. 5단계 파이프라인이 4종 AST와 4단 컴파일러를 거치며, 자기 치유 루프가 LLM의 실수를 체계적으로 교정하는 구조입니다.

**3장**에서 그 구조의 심장부인 Typia를 파헤칩니다. TypeScript 컴파일러가 소스 코드의 타입 하나를 분석해서 스키마, 파서, 검증기, 피드백 생성기를 전부 만들어냅니다. Qwen 3.5의 0%를 100%로 뒤집은 구체적 메커니즘이 여기에 있습니다.

**4장**에서 한 발 물러나 더 큰 질문을 던집니다. 이 패턴이 백엔드 너머에도 통하는가? 반도체, 화학공정, 건축, 제어시스템 — 검증기가 존재하는 공학 분야라면 어디든.

그리고 **5장**에서 왜 이 이야기가 Qwen Meetup에 있는지를 답합니다. 작은 모델은 약점이 아닙니다. 하네스 시스템의 최고의 QA 엔지니어입니다.

## 2. AutoBe — AI 백엔드 자동 생성 에이전트

### 2.1. AutoBe가 하는 일

[AutoBe](https://github.com/wrtnlabs/autobe)는 자연어로부터 프로덕션 수준의 백엔드를 자동 생성하는 오픈소스 AI 에이전트입니다. [Wrtn Technologies](https://wrtn.io)에서 개발했습니다.

"쇼핑몰 백엔드를 만들어줘. 상품 목록, 장바구니, 주문, 결제가 필요해." 이 한마디면 AutoBe가 다음을 모두 생성합니다:

- 요구사항 분석서 (SRS)
- 데이터베이스 스키마 (ERD)
- API 명세 (OpenAPI v3.2)
- E2E 테스트 코드
- 완전한 구현 코드
- 타입 안전 SDK

생성된 코드의 모든 줄이 컴파일됩니다. 결과물은 TypeScript + NestJS 기반의 완전히 동작하는 백엔드입니다.

### 2.2. LLM은 코드를 쓰지 않는다

대부분의 AI 코딩 에이전트는 LLM에게 "이 코드를 작성해"라고 지시하고, 반환된 텍스트를 그대로 소스 파일에 저장합니다. AutoBe는 다릅니다.

AutoBe는 **function calling**을 사용합니다. LLM은 자유 형식 텍스트를 생성하는 대신, 미리 정의된 구조 — JSON Schema — 를 채웁니다. 빈 페이지가 아니라 양식(form)을 작성하는 것입니다. LLM이 양식을 채우면, 컴파일러가 검증하고 실제 코드로 변환합니다. **LLM은 구조를 채우고, 컴파일러가 코드를 작성합니다.**

이 방식이 5단계 워터폴 파이프라인 전체에 걸쳐 적용됩니다.

| 단계 | LLM이 채우는 구조 | 컴파일러 검증 |
|------|-------------------|--------------|
| 요구사항 | [`AutoBeAnalyze`](https://github.com/wrtnlabs/autobe/blob/main/packages/interface/src/analyze/AutoBeAnalyze.ts) — 구조화된 SRS | 구조 검사 |
| 데이터베이스 | [`AutoBeDatabase`](https://github.com/wrtnlabs/autobe/blob/main/packages/interface/src/database/AutoBeDatabase.ts) — DB 스키마 AST | AutoBeDatabase 컴파일러 |
| API 설계 | [`AutoBeOpenApi`](https://github.com/wrtnlabs/autobe/blob/main/packages/interface/src/openapi/AutoBeOpenApi.ts) — OpenAPI v3.2 명세 | AutoBeOpenApi 컴파일러 |
| 테스트 | [`AutoBeTest`](https://github.com/wrtnlabs/autobe/blob/main/packages/interface/src/test/AutoBeTest.ts) — 30개 이상 표현식 타입 | AutoBeTest 컴파일러 |
| 구현 | 모듈화된 코드 (Collector/Transformer/Operation) | TypeScript 컴파일러 |

각 AST는 LLM이 생성할 수 있는 값의 범위를 엄격히 제한합니다 — 예를 들어 `AutoBeDatabase`의 필드 타입은 `"boolean" | "int" | "double" | "string" | "uri" | "uuid" | "datetime"` 7가지뿐이어서, LLM이 `"varchar"` 같은 임의의 타입을 생성할 수 없습니다.

40개 이상의 전문 AI 에이전트가 이 파이프라인을 수행합니다. 단순한 일직선이 아닙니다 — 단계 내부에서 나선형 루프가 돌며, 실패 시 자동으로 재생성과 교정을 반복합니다. 단계 간 의존성은 Step Counter 패턴으로 관리됩니다 — 상위 단계가 다시 실행되면 하위 단계가 자동으로 무효화되어, 데이터베이스 스키마 수정 시 API 명세부터 구현 코드까지 연쇄적으로 재생성됩니다.

### 2.3. 4단 컴파일러 검증

AutoBe의 100% 컴파일 보장은 4단 검증 시스템에서 나옵니다. 각 단계는 서로 다른 추상화 수준에서 검증합니다.

**1단계: AutoBeDatabase 컴파일러**

데이터베이스 AST의 구조적 무결성을 검증합니다. 중복 모델/필드 탐지, 참조 무결성 (외래키가 실존하는 모델을 가리키는지), 명명 규칙 준수 (모델은 snake_case, 관계는 camelCase), 인덱스 유효성 (인덱스 대상 필드가 존재하는지), 관계 설정의 정합성. 검증 통과 시 AST를 실제 DB 스키마 코드로 변환하고 다시 컴파일합니다.

```typescript
// 컴파일러가 반환하는 진단 정보의 구조
interface IError {
  path: "application.files[0]";          // 위치
  table: "shopping_customers" | null;    // 해당 모델
  field: "shopping_customer_id" | null;  // 해당 필드
  message: "상세한 오류 설명";            // 원인
}
```

**2단계: AutoBeOpenApi 컴파일러**

OpenAPI v3.2 명세의 유효성을 검증합니다. 데이터베이스 스키마와의 정합성 확인 — DTO 필드가 실제 모델 필드와 대응하는지, 모든 테이블에 API 오퍼레이션이 존재하는지. 경로 유일성, 스키마 참조 유효성 검사. 검증 통과 시 NestJS 템플릿, DTO 타입, 모듈 설정을 생성합니다.

**3단계: AutoBeTest 컴파일러**

테스트 AST의 유효성을 검증합니다. `IExpression`의 30개 이상 변종으로 구성된 E2E 테스트 코드가 올바른 구조를 갖추고 있는지, API 명세와 정합하는지 검증합니다. 검증 통과 시 실제 TypeScript 테스트 코드를 생성합니다.

**4단계: TypeScript 컴파일러**

최종 검증 관문입니다. 엄격 모드 (`strict null checks`, `no implicit any`)로 컴파일합니다. 증분 컴파일을 지원하여 이전 컴파일 결과를 재사용하면 15배 성능이 향상됩니다. 파일/줄/열 수준의 정밀한 진단 정보를 제공합니다. 동시 컴파일은 세마포어로 2개로 제한하여 시스템 과부하를 방지합니다.

네 컴파일러 모두, 실패 시 "어디서, 무엇이, 왜 잘못되었는지"를 구조화된 형태로 반환합니다. 이 진단 정보가 다음 절의 자기 치유 루프를 가능하게 합니다.

### 2.4. 자기 치유 루프

컴파일 실패는 끝이 아닙니다. AutoBe의 핵심 메커니즘은 **자기 치유 루프**입니다.

```
생성 → 컴파일 → 진단 추출 → 교정 → 재컴파일 → (성공할 때까지 반복)
```

1. LLM이 구조화된 데이터를 생성합니다
2. 컴파일러가 검증합니다
3. 실패 시, 정확한 위치와 원인을 담은 진단 정보를 추출합니다
4. 교정(Correct) 에이전트가 원본 코드 + 진단 정보를 받아 수정합니다
5. 다시 컴파일합니다
6. 성공할 때까지 반복합니다

이 루프는 계층적으로 중첩됩니다. 가장 복잡한 Realize(구현) 단계에는 4단계의 재시도 수준이 있습니다:

1. **인라인 재시도** — 생성 즉시 1회 재시도
2. **교정 루프** — 컴파일 오류 진단 기반 재귀적 교정
3. **외부 재시도 루프** — 실패한 오퍼레이션을 최대 2회 재처리
4. **선택적 재처리** — 40개 API 중 38개가 성공하면, 실패한 2개만 재처리

성공한 코드는 보존됩니다. 실패한 부분만 교정합니다.

여기에 Typia의 validation feedback이 function calling 수준에서의 정밀한 오류 교정을 더합니다. AutoBe의 컴파일러가 코드 수준에서의 최종 검증을 담당하고, Typia가 function calling 수준에서의 구조 검증을 담당합니다. 이 두 계층의 결합이 100% 컴파일의 원동력입니다. Typia의 역할에 대해서는 3장에서 자세히 다룹니다.

### 2.5. 채울 양식은 단순하지 않다

LLM이 채워야 하는 구조는 결코 단순하지 않습니다.

API 설계 시 LLM이 생성하는 **DTO 스키마 타입**은 API 요청/응답의 데이터 구조를 기술합니다 — "상품의 가격은 양의 정수, 이름은 문자열, 카테고리 목록은 문자열 배열." 이 타입을 정의하는 `IJsonSchema`는 10개 변종의 재귀적 유니온입니다:

```typescript
export type IJsonSchema =
  | IJsonSchema.IConstant
  | IJsonSchema.IBoolean
  | IJsonSchema.IInteger
  | IJsonSchema.INumber
  | IJsonSchema.IString
  | IJsonSchema.IArray      // items: IJsonSchema ← 재귀
  | IJsonSchema.IObject     // properties: Record<string, IJsonSchema> ← 재귀
  | IJsonSchema.IReference
  | IJsonSchema.IOneOf      // oneOf: IJsonSchema[] ← 재귀
  | IJsonSchema.INull;
```

10개 변종, 무한 재귀 중첩. 이 타입에 대한 첫 시도 function calling 성공률이 6.75%입니다.

테스트 단계는 복잡성이 한 단계 더 올라갑니다. E2E 테스트 코드는 "이 API를 호출하고, 응답 상태가 200인지 확인하고, 본문의 items 배열 길이가 0보다 큰지 검증하라" 같은 로직을 표현해야 합니다. 이를 담는 `IExpression` 타입:

```typescript
export type IExpression =
  | IBooleanLiteral   | INumericLiteral    | IStringLiteral     // 리터럴
  | IArrayLiteralExpression  | IObjectLiteralExpression          // 복합 리터럴
  | INullLiteral      | IUndefinedKeyword                       // null/undefined
  | IIdentifier       | IPropertyAccessExpression               // 접근자
  | IElementAccessExpression | ITypeOfExpression                 // 접근/연산
  | IPrefixUnaryExpression   | IPostfixUnaryExpression           // 단항 연산
  | IBinaryExpression                                            // 이항 연산
  | IArrowFunction    | ICallExpression    | INewExpression      // 함수
  | IArrayFilterExpression   | IArrayForEachExpression           // 배열 연산
  | IArrayMapExpression      | IArrayRepeatExpression            // 배열 연산
  | IPickRandom       | ISampleRandom      | IBooleanRandom     // 랜덤 생성
  | IIntegerRandom    | INumberRandom      | IStringRandom      // 랜덤 생성
  | IPatternRandom    | IFormatRandom      | IKeywordRandom     // 랜덤 생성
  | IEqualPredicate   | INotEqualPredicate                      // 단언
  | IConditionalPredicate    | IErrorPredicate;                  // 단언
```

30개 이상 변종의 재귀 중첩. 프로그래밍 언어 수준의 복잡성을 단일 function call로 처리해야 합니다.

### 2.6. 스키마 스펙이 곧 프롬프트다

기존 AI 에이전트에서 "프롬프트"란 자연어 지시문입니다. "당신은 백엔드 개발 전문가입니다. 코드 작성 시 다음 규칙을 따르세요..."

AutoBe에서 프롬프트 역할을 하는 것은 자연어가 아니라 **스키마 스펙** 자체입니다. `AutoBeDatabase`의 `stance` 열거형이 모델에게 어떤 종류의 테이블을 만들어야 하는지 알려주고, `IJsonSchema`의 10개 변종이 DTO를 어떤 구조로 기술해야 하는지 정의하고, `IExpression`의 30개 변종이 테스트 코드를 어떤 문법으로 표현해야 하는지 규정합니다.

자연어 프롬프트는 모호하고, 모델마다 해석이 달라지며, 지켰는지 검증할 수 없습니다. 스키마 스펙은 모호함이 없고, 모델에 무관하며, 기계적으로 검증 가능합니다. 시스템 프롬프트가 쓸모없다는 말이 아닙니다 — 스키마 스펙이 프롬프트보다 **더 강력한 지시 수단**이라는 것입니다.

**스키마 스펙이 곧 새 시대의 프롬프트입니다.**

### 2.7. 4개 Qwen 모델, 모두 100%

AutoBe는 현재 4개의 Qwen 모델을 대상으로 테스트합니다. 모두 컴파일에 성공합니다.

## 3. Typia — 0%를 100%로 만드는 인프라

2장에서 자연스럽게 등장했던 것들 — 스키마 생성, 깨진 JSON 복구, 타입 교정, 정밀 오류 피드백 — 이 모든 것을 누가 담당할까요?

[Typia](https://github.com/samchon/typia)입니다. Typia는 단순한 런타임 라이브러리가 아닙니다. TypeScript 컴파일러의 타입 분석기를 직접 활용하는 **컴파일러 라이브러리**입니다. 소스 코드의 타입 정의를 컴파일 타임에 분석하여, JSON Schema · 검증기 · 파서 · 피드백 생성기를 자동으로 만들어냅니다. 타입 하나 정의하면 나머지는 컴파일러가 전부 해결합니다.

`qwen3-coder-next`의 6.75% 성공률, `qwen3.5`의 0% 성공률을 어떻게 100%로 만드는지, 그 내부를 세밀하게 살펴봅시다.

### 3.1. TypeScript 타입에서 Function Calling 스키마까지

Function calling에는 LLM에게 "이 구조로 데이터를 달라"고 알려주는 JSON Schema가 필요합니다. 보통 개발자가 타입을 정의하고, 별도로 스키마를 작성하고, 둘을 영원히 동기화해야 합니다.

Typia는 이 과정을 자동화합니다. TypeScript 타입을 정의하면, Typia가 **컴파일 타임에** 검증 코드와 JSON Schema를 **자동 생성**합니다 — 런타임 리플렉션이 아니라 TypeScript 컴파일러의 타입 분석기를 직접 활용합니다.

원리를 먼저 보겠습니다. `typia.is<T>()`를 호출하면, 컴파일 시점에 타입 정보를 분석하여 최적화된 검증 코드로 변환됩니다:

<Tabs items={["컴파일 전: TypeScript", "컴파일 후: JavaScript"]}>
  <Tabs.Tab>
```typescript
import typia, { tags } from "typia";

interface IMember {
  id: string & tags.Format<"uuid">;
  email: string & tags.Format<"email">;
  age: number &
    tags.Type<"uint32"> &
    tags.ExclusiveMinimum<19> &
    tags.Maximum<100>;
}

const check: boolean = typia.is<IMember>(input);
```
  </Tabs.Tab>
  <Tabs.Tab>
```javascript
((input) => {
  return (
    "object" === typeof input &&
    null !== input &&
    "string" === typeof input.id &&
    /^[0-9a-f]{8}-[0-9a-f]{4}-[1-5].*$/.test(input.id) &&
    "string" === typeof input.email &&
    /^[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}$/.test(input.email) &&
    "number" === typeof input.age &&
    Number.isInteger(input.age) &&
    input.age >= 0 &&
    19 < input.age &&
    100 >= input.age

```
  </Tabs.Tab>

`typia.is<IMember>(input)` 한 줄이 컴파일 타임에 UUID 정규식, 이메일 정규식, 정수 검사, 범위 검사를 담은 최적화된 코드로 변환됩니다. 런타임에는 타입 정보가 사라지는 TypeScript의 한계를 컴파일러 플러그인으로 극복한 것입니다.

이 원리가 function calling에도 그대로 적용됩니다. `typia.llm.parameters<T>()`는 같은 타입 분석으로 JSON Schema를 생성합니다:

<Tabs items={["컴파일 전: TypeScript", "컴파일 후: JSON Schema"]}>

```typescript
  age: number & tags.Type<"uint32"> & tags.ExclusiveMinimum<18>;
  email: string & tags.Format<"email">;

```

  <Tabs.Tab>

```json
      "exclusiveMinimum": 18
```

**JSDoc 주석이 `description` 필드가 됩니다.** LLM은 이 설명을 읽고 어떤 값을 생성할지 결정합니다. **타입 제약이 검증 규칙이 됩니다.** `ExclusiveMinimum<18>`은 "> 18" 규칙이 되고, `Format<"email">`은 이메일 형식 검사가 됩니다. 하나의 타입 정의가 LLM 가이드와 검증 규칙을 동시에 생성합니다.

클래스 수준에서는 `typia.llm.application<T>()`로 전체 API를 스키마화할 수 있습니다:

```typescript
import { LlmJson } from "@typia/utils";
import typia from "typia";

class ShoppingOrderController {
  /** 주문을 생성합니다 */
  create(input: IShoppingOrderCreate): void;
}

const app = typia.llm.application<ShoppingOrderController>();
const func = app.functions[0];

// 모든 공개 메서드에 parse(), validate()가 내장
const data = func.parse(llmOutput);        // 깨진 JSON 복구 + 타입 교정
const result = func.validate(data);        // 스키마 위반 감지
if (result.success === false) {
  const feedback = LlmJson.stringify(result); // LLM 가독 피드백 생성
}
```

**타입이 곧 스키마입니다.** LLM이 보는 제약과 검증기가 적용하는 제약이 항상 동일합니다 — 같은 소스에서 나오니까요.

이것이 핵심입니다. Typia 컴파일러가 소스 코드의 타입을 분석하여 생성한 이 스키마가, 이후에 나올 모든 런타임 기능의 동력입니다. `parse()`가 깨진 JSON을 복구하고 타입을 교정할 때 참조하는 스키마, `validate()`가 오류를 진단할 때 비교 대상으로 사용하는 스키마 — 전부 컴파일 타임에 타입으로부터 자동 생성된 같은 스키마입니다. 수동 작성이 아니라 컴파일러 출력이기에, 타입과 스키마가 어긋날 수 없습니다.

### 3.2. 6.75%의 원인: 구조의 복잡성

2장에서 본 `IJsonSchema`의 10개 변종과 `IExpression`의 30개 이상 변종. 왜 첫 시도 성공률이 이렇게 낮을까요?

재귀적 유니온 타입은 **조합 폭발**(combinatorial explosion)을 일으킵니다. 10개 변종이 3단계 중첩되면 1,000개의 가능한 경로가 생깁니다. 30개 변종이라면 27,000개. LLM이 한 번에 올바른 경로를 선택할 확률은 구조적으로 낮습니다.

게다가 유니온 타입에서는 미묘한 오류가 빈발합니다:
- 올바른 변종을 선택했지만 하위 필드의 타입을 틀림
- 재귀 깊이에서 변종을 혼동
- 필수 필드 누락
- 객체를 문자열로 직렬화 (double-stringify)

이런 오류는 "구조적으로 올바르지만 의미적으로 틀린" 경우여서, 단순한 JSON Schema 검증으로는 정확한 피드백을 주기 어렵습니다.

6.75%는 이 구조적 복잡성의 자연스러운 결과입니다. 문제는 첫 시도가 아니라, **실패 후 무엇이 일어나느냐**입니다.

### 3.3. Lenient JSON Parsing: 깨진 JSON 복구

LLM은 완벽한 JSON을 생성하지 않습니다. LLM은 토큰 단위로 텍스트를 생성하는 언어 모델이지, JSON 생성기가 아닙니다. 괄호를 닫지 않고, 쉼표를 잘못 놓고, JSON 앞에 "Here is your answer:"를 붙이고, Markdown 코드 블록으로 감쌉니다.

`JSON.parse()`는 이 모든 것을 거부합니다. Typia의 `ILlmFunction.parse()`는 모든 경우를 처리합니다:

| 문제 | 예시 | 처리 |
|------|------|------|
| 닫히지 않은 괄호 | `{"name": "John"` | 자동 닫기 |
| 후행 쉼표 | `[1, 2, 3, ]` | 무시 |
| JavaScript 주석 | `{"a": 1 /* comment */}` | 제거 |
| 따옴표 없는 키 | `{name: "John"}` | 허용 |
| 불완전한 키워드 | `{"done": tru` | `true`로 완성 |
| 설명 접두사 | `Here is your JSON: {"a": 1}` | 건너뜀 |
| Markdown 코드 블록 | `` ```json\n{"a": 1}\n``` `` | 내부 추출 |

실제로 이런 문제들이 동시에 발생한 LLM 출력에 `func.parse()`를 호출하면:

```typescript
import { dedent } from "@typia/utils";
import typia, { ILlmApplication, ILlmFunction, tags } from "typia";

const app: ILlmApplication = typia.llm.application<OrderService>();
const func: ILlmFunction = app.functions[0];

// LLM sometimes returns malformed JSON with wrong types
const llmOutput = dedent`
  > LLM sometimes returns some prefix text with markdown JSON code block.
    I'd be happy to help you with your order! 😊
    \`\`\`json
  {
    "order": {
      "payment": "{\\"type\\":\\"card\\",\\"cardNumber\\":\\"1234-5678", // unclosed string & bracket
      "product": {
        name: "Laptop", // unquoted key
        price: "1299.99", // wrong type (string instead of number)
        quantity: 2, // trailing comma
      },
      "customer": {
        // incomplete keyword + unclosed brackets
        "name": "John Doe",
        "email": "john@example.com",
        vip: tru
  \`\`\` `;

const result = func.parse(llmOutput);
if (result.success) console.log(result);

interface IOrder {
  payment: IPayment;
  product: {
    name: string;
    price: number & tags.Minimum<0>;
    quantity: number & tags.Type<"uint32">;
  };
  customer: {
    name: string;
    email: string & tags.Format<"email">;
    vip: boolean;
  };
}

type IPayment =
  | { type: "card"; cardNumber: string }
  | { type: "bank"; accountNumber: string };

declare class OrderService {
  /**
   * Create a new order.
   *
   * @param props Order properties
   */
  createOrder(props: { order: IOrder }): { id: string };
}
```

핵심적인 차이점이 있습니다. 대부분의 JSON 복구 도구(jsonrepair, dirty-json, LangChain의 `parse_partial_json`)는 **문자열 수준**에서 작동합니다 — 후행 쉼표 정리, 괄호 닫기, Markdown 제거 후 `JSON.parse()`로 넘깁니다. 이중 문자열화(double-stringified)된 값 `"{\"type\":\"card\"}"` 는 이미 유효한 JSON (문자열)이므로 그대로 통과합니다. 스키마 없이는 이것이 객체여야 한다는 것을 알 수 없습니다.

Typia의 `parse()`는 다릅니다. 3.1절에서 컴파일러가 타입으로부터 생성한 **스키마를 참조하며** 탐욕적으로(greedily) 파싱합니다. 스키마가 객체를 기대하는 곳에서 문자열을 만나면, 그 문자열에 대해 `parse()`를 재귀적으로 호출합니다. 파싱과 교정이 서로를 재귀적으로 호출하며 — **스키마 기반 재귀 순환** — 겹겹이 쌓인 stringify를 자연스럽게 풀어냅니다. 이중이든 삼중이든.

`parse()`는 JSON 복구뿐 아니라 **스키마 기반 타입 교정**도 동시에 수행합니다. LLM은 타입을 자주 틀립니다 — `"42"` (문자열)이 와야 할 곳에 `42` (숫자), `"true"` (문자열)이 와야 할 곳에 `true` (불리언). 단순 캐스팅으로는 해결이 안 됩니다. `"42"`가 숫자가 되어야 하는지, 문자열로 남아야 하는지는 해당 필드의 스키마에 전적으로 달려 있고, 그 스키마는 Typia 컴파일러가 TypeScript 타입으로부터 자동 생성한 것입니다.

| LLM 출력 | 스키마 기대 타입 | `parse()` 교정 결과 |
|----------|---------|------|
| `"42"` | `number` 또는 `integer` | `42` |
| `"true"` / `"false"` | `boolean` | `true` / `false` |
| `"null"` | `null` | `null` |
| `"{\"x\": 1}"` | `object` | `{ x: 1 }` (재귀 파싱) |
| `"[1, 2, 3]"` | `array` | `[1, 2, 3]` (재귀 파싱) |

### 3.4. Qwen 3.5의 0% 문제: Double-Stringify

`qwen3.5` 시리즈에서 더 극적인 사례가 있습니다.

[Typia 문서](https://typia.io/docs/llm/application/#lenient-json-parsing)의 function calling 예시입니다:

```typescript
interface IOrder {
  payment: IPayment;
  product: {
    name: string;
    price: number & tags.Minimum<0>;
    quantity: number & tags.Type<"uint32">;
  };
  customer: {
    name: string;
    email: string & tags.Format<"email">;
    vip: boolean;
  };
}
type IPayment =
  | { type: "card"; cardNumber: string }
  | { type: "bank"; accountNumber: string };
```

LLM이 실제로 반환하는 것:

```typescript
const llmOutput = `
  > LLM sometimes returns some prefix text with markdown JSON code block.
 
  I'd be happy to help you with your order! 😊
 
  \`\`\`json
  {
    "order": {
      "payment": "{\"type\":\"card\",\"cardNumber\":\"1234-5678", // unclosed string & bracket
      "product": {
        name: "Laptop", // unquoted key
        price: "1299.99", // wrong type (string instead of number)
        quantity: 2, // trailing comma
      },
      "customer": {
        // incomplete keyword + unclosed brackets
        "name": "John Doe",
        "email": "john@example.com",
        vip: tru
  \`\`\`
```

Markdown 감싸기, 설명 접두사, 따옴표 없는 키, 후행 쉼표, `tru` (`true` 대신), 닫히지 않은 괄호 — 그리고 `payment`가 **이중 문자열화(double-stringified)**되어 있습니다. `{"type": "card", ...}` (객체) 대신 `"{\"type\": \"card\", ...}"` (JSON을 담은 문자열)를 생성한 것입니다. 하나의 출력에 7가지 문제.

이중 문자열화가 성공률을 **0%**로 만듭니다. 다른 오류는 간헐적이지만, `anyOf` 이중 문자열화는 **100% 일관적** — 모든 `anyOf` 필드에서, 매번 발생합니다. Qwen만의 문제도 아닙니다. Anthropic의 Claude도 `oneOf`에서 같은 현상을 보입니다. 모든 모델 패밀리에 유니온 타입의 사각지대가 있습니다.

Typia의 `parse()`가 이 모든 것을 단일 호출로 처리합니다 — 깨진 JSON 복구, 타입 교정, 이중 문자열화 해제. 모델 변경 없음. 프롬프트 튜닝 없음. 이것이 Qwen 3.5가 0%에서 100%로 간 방법입니다.

### 3.5. Validation Feedback: 정밀한 오류 피드백

파싱과 교정을 거쳐도 값 자체가 틀릴 수 있습니다. 음수 가격, 이메일이 아닌 문자열, 정수여야 하는 곳의 소수.

Typia의 `ILlmFunction.validate()`는 스키마 위반을 감지하고 **어디서 왜** 틀렸는지를 정확히 알려줍니다:

```typescript
import { LlmJson } from "@typia/utils";
import typia, { ILlmApplication, ILlmFunction, IValidation, tags } from "typia";

const app: ILlmApplication = typia.llm.application<OrderService>();
const func: ILlmFunction = app.functions[0];

// LLM generated invalid data
const input = {
  order: {
    payment: { type: "card", cardNumber: 12345678 }, // should be string
    product: {
      name: "Laptop",
      price: -100, // violates Minimum<0>
      quantity: 2.5, // should be uint32
    },
    customer: {
      name: "John Doe",
      email: "invalid-email", // violates Format<"email">
      vip: "yes", // should be boolean
    },
  },
};

// Validate and format errors for LLM feedback
const result: IValidation = func.validate(input);
if (result.success === false) {
  const feedback: string = LlmJson.stringify(result);
  console.log(feedback);
}

interface IOrder {
  payment: IPayment;
  product: {
    name: string;
    price: number & tags.Minimum<0>;
    quantity: number & tags.Type<"uint32">;
  };
  customer: {
    name: string;
    email: string & tags.Format<"email">;
    vip: boolean;
  };
}

type IPayment =
  | { type: "card"; cardNumber: string }
  | { type: "bank"; accountNumber: string };

declare class OrderService {
  /**
   * Create a new order.
   *
   * @param props Order properties
   */
  createOrder(props: { order: IOrder }): { id: string };
}
```

"order 안의 product 안의 price는 ≥ 0이어야 하는데 -100을 줬습니다."

`LlmJson.stringify()`는 이 오류들을 LLM의 원본 JSON 위에 `// ❌` 인라인 주석으로 렌더링합니다:

```json
{
  "order": {
    "payment": {
      "type": "card",
      "cardNumber": 12345678 // ❌ [{"path":"$input.order.payment.cardNumber","expected":"string"}]
    },
    "product": {
      "name": "Laptop",
      "price": -100, // ❌ [{"path":"$input.order.product.price","expected":"number & Minimum<0>"}]
      "quantity": 2.5 // ❌ [{"path":"$input.order.product.quantity","expected":"number & Type<\"uint32\">"}]
    },
    "customer": {
      "name": "John Doe",
      "email": "invalid-email", // ❌ [{"path":"$input.order.customer.email","expected":"string & Format<\"email\">"}]
      "vip": "yes" // ❌ [{"path":"$input.order.customer.vip","expected":"boolean"}]
    }
  }
}
```

`cardNumber`는 문자열이어야 하는데 숫자. `price`는 ≥ 0이어야 함. `quantity`는 양의 정수여야 함. `email`은 유효한 이메일이 아님. `vip`는 불리언이어야 함. 5개 오류, 각각 정확한 경로와 기대 타입이 명시됩니다.

LLM은 자신의 JSON 위에서 정확히 어디가 틀렸는지 봅니다. 전체를 다시 쓸 필요 없이 표시된 5개 필드만 고치면 됩니다. 정밀하고, 구조화되고, 즉각 조치 가능한 피드백입니다.

### 3.6. 완전한 피드백 루프

모든 것을 하나의 루프로 결합합니다:

```typescript
async function callWithFeedback(
  llm: LLM,
  func: ILlmFunction,
  prompt: string,
  maxRetries: number = 10,
): Promise<unknown> {
  let feedback: string | null = null;

  for (let i = 0; i < maxRetries; i++) {
    // 1. LLM에 function call 요청 (이전 피드백 포함)
    const rawOutput = await llm.call(prompt, feedback);

    // 2. Lenient JSON 파싱 + 타입 교정
    const parsed = func.parse(rawOutput);
    if (!parsed.success) {
      feedback = `JSON 파싱 실패: ${JSON.stringify(parsed.errors)}`;
      continue;
    }

    // 3. 스키마 검증
    const validated = func.validate(parsed.data);
    if (!validated.success) {
      // 4. 구조화된 피드백 생성 (// ❌ 인라인 주석)
      feedback = LlmJson.stringify(validated);
      continue;
    }

    // 5. 성공
    return validated.data;
  }
  throw new Error("최대 재시도 횟수 초과");
}
```

`parse()`가 깨진 JSON을 복구하고 1차 타입 교정을 수행합니다. `validate()`가 스키마 위반을 잡습니다. `LlmJson.stringify()`가 LLM이 읽을 수 있는 형태로 오류를 렌더링합니다. LLM이 스스로 교정하고 재시도합니다.

이것이 6.75%를 100%로 만드는 완전한 루프입니다.

### 3.7. 하네스 엔지니어링: AutoBe + Typia의 결합

여기서 비로소 **하네스(harness)**라는 개념이 완성됩니다.

등반 하네스는 당신을 더 강하게 만들지 않습니다 — 당신의 힘을 안전하게 만듭니다. 테스트 하네스는 코드를 올바르게 만들지 않습니다 — 버그를 가시화합니다. Function calling 하네스는 LLM을 더 똑똑하게 만들지 않습니다 — **LLM의 실수를 교정 가능하게** 만듭니다.

AutoBe와 Typia의 결합이 이 하네스를 구성합니다:

**Typia 계층** (function calling 수준):
- 타입 → 스키마 자동 생성
- 깨진 JSON 복구 (lenient parsing)
- 스키마 기반 타입 교정 (type coercion)
- 정밀 오류 피드백 (validation feedback)

**AutoBe 계층** (시스템 수준):
- 4종 AST + 4단 컴파일러 검증
- 자기 치유 루프 (진단 → 교정 → 재검증)
- 계층적 오케스트레이션 (40+ 에이전트 협업)
- 배치 처리 + 프롬프트 캐싱 최적화

Typia가 function calling의 입출력을 견고하게 만들고, AutoBe가 시스템 전체의 정합성을 보장합니다. 이 두 계층의 결합이 확률적 모델을 감싸는 결정론적 루프 — 하네스 — 를 완성합니다.

하나의 TypeScript 타입을 정의하면 Typia **컴파일러**가 나머지를 전부 처리합니다:

1. **컴파일 타임: 소스 코드 분석** — TypeScript 타입을 분석하여 JSON Schema · 검증기 · 파서 코드를 자동 생성
2. **스키마 생성** — `typia.llm.parameters<T>()`, `typia.llm.application<T>()`
3. **파싱 + 타입 교정** — `ILlmFunction.parse()` (컴파일러가 생성한 스키마로 깨진 JSON 복구, 타입 교정, double-stringify 해제를 한 번에)
4. **검증** — `ILlmFunction.validate()` (같은 스키마로 위반 감지)
5. **피드백 생성** — `LlmJson.stringify()` (LLM 가독 `// ❌` 인라인 진단)

**타입이 곧 스키마이자, 검증기이자, 프롬프트입니다. 하네스는 그 주위의 모든 것입니다.**

## 4. Function Calling 예찬론

2장과 3장은 **어떻게** 작동하는지를 보여줬습니다. 이제: **왜** function calling이 이토록 강력한지.

### 4.1. 자연어 vs 타입

자연어는 모호하도록 진화했습니다. 은유, 뉘앙스, 공손함, 유머 — 모두 모호성 위에서 작동합니다. "그냥 이쁘게 해줘"는 사람 사이에서는 통합니다.

프로그래밍 언어는 모호성을 제거하도록 설계되었습니다. "그냥 이쁘게 해줘"는 컴파일되지 않습니다.

**사람이 자연어로 소통하면 오해가 생깁니다. 타입으로 소통하면 오해가 없습니다.**

프롬프트로 제약을 표현하면:
> "age 필드는 18보다 큰 양의 정수여야 합니다. 숫자 필드에 문자열 타입을 사용하지 마세요. 모든 필수 필드가 있어야 합니다..."

"18보다 큰"이 >18인지 ≥18인지? LLM이 이 규칙을 따랐는지 출력을 직접 검사하지 않으면 알 수 없습니다. 스키마가 커지면 이런 규칙은 끝없이 늘어납니다.

타입으로 제약을 표현하면:
```typescript
interface IMember {
  /** 19세 이상 성인만 가입 가능 */
  age: number & Type<"uint32"> & ExclusiveMinimum<18>;
}
```

`ExclusiveMinimum<18>`은 >18입니다. 정수입니다. 필수입니다. 모호함이 없고, 기계적으로 검증 가능합니다.

정밀성이 요구되는 도메인에서, 타입 제약은 자연어 지시가 줄 수 없는 확실성을 제공합니다.

### 4.2. 분홍 코끼리 문제

프롬프트 기반 AI 에이전트를 만들어봤다면, 금지 규칙을 작성해본 적이 있을 것입니다:

- "유틸리티 함수를 만들지 마세요"
- "`any` 타입을 사용하지 마세요"
- "순환 의존성을 만들지 마세요"

"분홍 코끼리를 생각하지 마세요." 가장 먼저 떠오르는 것이 분홍 코끼리입니다. LLM에게 "X를 하지 마"라고 말하면, X가 주의의 중심에 놓입니다. 금지된 패턴을 피하려면 먼저 그 패턴을 떠올려야 하는데, 이것이 역설적으로 해당 패턴의 생성 확률을 높입니다. 토큰 예측의 본질입니다.

이 사실을 알더라도, 프롬프트에서 금지 규칙을 피할 수 없습니다. "X를 하지 마"가 자연어가 제약을 표현하는 유일한 수단이니까요.

**스키마에서는 이 문제가 사라집니다.**

"`any` 타입을 사용하지 마세요"라고 말할 필요가 없습니다 — 스키마에 `any`가 없으면 LLM이 물리적으로 생성할 수 없습니다. "유틸리티 함수를 만들지 마세요"라고 말할 필요가 없습니다 — 유틸리티 함수를 넣을 슬롯이 없으면 그것으로 끝입니다. 필드 타입이 `"boolean" | "int" | "double" | "string" | "uri" | "uuid" | "datetime"` — 7개 선택지 — 로 제한되면, LLM이 `"varchar"`를 쓸 경로가 존재하지 않습니다.

금지(prohibition)가 아니라, **부재(absence)**. 프롬프트는 원하지 않는 것을 금지합니다. 스키마는 원하는 것만 허용합니다.

이것이 function calling의 가장 깊은 이점입니다: 모델의 경향과 싸우는 것이 아니라, 원치 않는 출력을 구조적으로 불가능하게 만듭니다.

### 4.3. 모델 중립성

프롬프트 엔지니어링은 본질적으로 모델 종속적입니다. GPT에 최적화된 프롬프트는 Claude에서 다르게 동작하고, Qwen에서 또 다르게 동작합니다. 새 모델이 나올 때마다 프롬프트 재작성이 일상입니다.

Function calling 기반 접근은 모델 중립적입니다. JSON Schema는 어떤 모델이 읽든 같은 의미입니다. 검증 피드백 루프가 모델 간 성능 차이를 흡수합니다. 강한 모델은 1–2회 시도로 수렴하고, 약한 모델은 3–4회 걸리지만, 둘 다 100%에 도달합니다.

AutoBe가 Qwen, GLM, DeepSeek, OpenAI 모델을 **같은 스키마, 같은 파이프라인**으로 실행하여 모두 100% 컴파일을 달성한 것이 이 중립성의 증거입니다. 모델별 프롬프트 튜닝은 한 번도 하지 않았습니다.

이것은 모델 선택의 성격을 바꿉니다. "이 모델이 이 작업을 할 수 있는가?" — 능력 질문에서, "어떤 모델이 가장 비용 효율적인가?" — **비용 최적화 문제**: `평균 재시도 횟수 × 시도당 토큰 수 × 토큰당 단가`로 전환됩니다.

### 4.4. 핵심: 검증 가능성

하나의 맥락이 모든 것을 관통합니다.

Function calling의 근본적인 이점은 **LLM의 출력을 소프트웨어 공학의 영역으로 가져온다**는 것입니다.

자유 형식 텍스트 출력은 정확성을 AI 문제로 만듭니다. 파싱이 퍼지합니다. 검증이 퍼지합니다. 교정이 퍼지합니다.

구조화된 출력은 정확성을 **공학 문제**로 만듭니다:

1. **검증이 결정론적** — JSON Schema 검증은 명확한 pass/fail
2. **피드백이 정밀** — "필드 X는 타입 Y여야 하는데 Z를 줬습니다"
3. **교정이 수렴** — 정밀한 피드백이 모델로 하여금 해당 부분만 수정하게 함

모델은 여전히 확률적입니다. 여전히 실수합니다. 하지만 **모델을 감싸는 구조가 결정론적**이므로, 과정은 100%로 수렴합니다.

> **타입 스키마 + 결정론적 검증기 + 구조화된 피드백 = 하네스**

프롬프트 엔지니어링은 확률적 부분을 신뢰할 수 있게 만들려 합니다. Function calling은 결정론적 부분을 완벽하게 만듭니다. 정밀성이 요구되는 도메인에서, 후자가 이깁니다: 6.75% → 100%.

### 4.5. 이 패턴은 보편적이다

이 패턴이 코드 생성에만 적용될까요? 아닙니다. 출력이 기계적으로 검증 가능한 모든 도메인에 적용됩니다.

#### 4.5.1. 적용 가능한 도메인

AutoBe의 Database, Interface, Test, Realize 단계가 모두 이 범주에 속합니다. 컴파일러가 검증기 역할을 하여 100% 정확성을 보장합니다.

소프트웨어만의 이야기가 아닙니다. "맞다/틀리다"를 기계적으로 판정할 수 있는 모든 분야에서 같은 구조가 가능하며, 검증 비용에 따른 자연스러운 계층이 존재합니다:

| 도메인 | 빠름 (ms) | 중간 (sec) | 심층 (min+) |
|--------|----------|-------------|------------|
| 소프트웨어 | 타입 검사 | 컴파일 | 테스트 실행 |
| 반도체 | DRC | LVS | SPICE 시뮬레이션 |
| 화학공정 | 물질수지 | 에너지수지 | 공정 시뮬레이션 |
| 인테리어 | 치수/통행폭 | 건축법규, 충돌 탐지 | 조명/HVAC 시뮬레이션 |
| 제어시스템 | 전달함수 유효성 | 안정성/마진 분석 | 시간 영역 시뮬레이션 |

가장 저렴한 검증기를 먼저 실행하고, 오류를 고치고, 다음 단계로 넘어가는 것이 자연스러운 전략입니다.

#### 4.5.2. 다른 도메인의 구체적 타입

위 표를 개관으로 보여줬습니다. 이것이 구체적인 타입으로는 어떻게 생겼는지 — 각각 수십 년간 검증기가 정제된 분야입니다.

**반도체** — 칩 설계의 물리적 규칙은 비타협적입니다:

```typescript
interface IChipLayout {
  technology_node: "5nm" | "7nm" | "14nm" | "28nm";
  blocks: IBlock[];
  connections: IConnection[];
}

interface IBlock {
  type: "logic" | "memory" | "io" | "analog" | "pll";
  position: IPoint2D;
  dimensions: IDimension;
  sub_blocks: IBlock[];  // 재귀적 계층
}
```

DRC(빠름), LVS(중간), SPICE 시뮬레이션(느림). 모두 결정론적.

**화학공정** — 보존 법칙이 절대적 검증기입니다:

```typescript
interface IProcessStream {
  temperature: number & Minimum<0>;          // 켈빈
  pressure: number & Minimum<0>;             // Pa
  composition: IComponent[];                 // 합이 1.0이어야 함
  phase: "liquid" | "vapor" | "solid" | "two_phase";
  flow_rate: number & Minimum<0>;            // kg/s
}

interface IUnitOperation {
  type: "reactor" | "distillation" | "heat_exchanger"
    | "compressor" | "pump" | "mixer" | "splitter";
  inlet_streams: IProcessStream[];
  outlet_streams: IProcessStream[];          // 물질수지: Σin = Σout
  energy_duty: number;                       // 에너지수지
}
```

질량 보존 (Σ 입구 = Σ 출구), 에너지 수지, 열역학적 정합성 — 물리 법칙이지, 의견이 아닙니다. ASPEN, HYSYS 같은 도구가 40년 넘게 결정론적 검증을 제공해왔습니다.

**인테리어** — 미학 아래 강성 제약이 공간을 정의합니다:

```typescript
interface IRoom {
  type: "bedroom" | "living" | "kitchen" | "bathroom"
    | "office" | "hallway" | "storage";
  dimensions: IDimension3D;
  openings: IOpening[];
  fixtures: IFixture[];
}

interface IOpening {
  type: "door" | "window" | "sliding_door" | "arch";
  width: number & Minimum<0>;      // 문 ≥ 900mm (접근성)
  height: number & Minimum<0>;
  position: IPoint3D;
  swing_direction?: "inward" | "outward" | "sliding";
}

interface IFixture {
  type: "cabinet" | "counter" | "appliance"
    | "furniture" | "lighting" | "plumbing";
  position: IPoint3D;
  dimensions: IDimension3D;
  clearance_required: number;       // 최소 여유 공간 (mm)
}
```

최소 통행폭 (800mm), 접근성을 위한 문 폭 (≥900mm), 방화구획 규정, 비상 대피 거리. Revit 같은 BIM 도구가 수십 년간 충돌 탐지를 제공해왔습니다.

**제어시스템** — 안정성은 수학적으로 증명 가능합니다:

```typescript
interface IControlLoop {
  type: "PID" | "MPC" | "LQR" | "feedforward" | "cascade";
  plant_model: ITransferFunction;
  setpoint: number;
  sampling_rate: number & Minimum<0>;        // Hz
  constraints: IConstraint[];
}

interface ITransferFunction {
  numerator: number[];                       // 다항식 계수
  denominator: number[];                     // 차수 ≥ 분자
  delay: number & Minimum<0>;               // 전송 지연 (sec)
}
```

보드 선도, 나이퀴스트 선도, 극점 배치: 60년 넘는 분석 도구 역사. 전달함수 유효성(빠름) → 안정성/이득·위상 마진(중간) → 시간 영역 시뮬레이션(심층).

이 타입들을 보세요. 모두 열거형 변종을 가진 `type` 필드가 있습니다 — `"logic" | "memory" | ...`, `"reactor" | "distillation" | ...`, `"bedroom" | "living" | ...`, `"PID" | "MPC" | ...`. 여럿이 재귀적으로 중첩됩니다. AutoBe의 `IJsonSchema`와 `IExpression`과 같은 유니온 + 트리 구조입니다. 우연이 아닙니다 — 공학 데이터의 본질입니다. 부록 A.3에서 그 이유를 설명합니다.

> **참고**: 위 도메인 예시들은 AI가 추천한 것입니다 — 모두 수십 년간 결정론적 검증기가 존재해온 공학 분야여서 원칙적으로 같은 구조가 적용됩니다. 다만 저는 개발자이지 도메인 전문가가 아니므로, 구체적인 내용은 참고 수준으로 봐주세요.

---

#### 4.5.3. 적용 불가능한 도메인

이 접근에는 명확한 한계가 있습니다.

첫째, **결정론적 검증기가 없는 도메인.** 창의적 글쓰기, 감성 지능, 전략적 의사결정. "좋은 소설"이나 "현명한 사업 결정"에 대한 검증기는 없습니다. 검증기가 없으면 피드백 루프가 없고, 피드백 루프가 없으면 이 구조가 성립하지 않습니다.

둘째, **구조를 구축하는 비용이 불확실성을 감수하는 비용을 초과할 때.** 정밀한 타입 설계, 컴파일러 통합, 피드백 포매팅에는 선행 투자가 필요합니다. 정확성 요건이 느슨한 일회성 작업에는 잘 작성된 프롬프트가 더 적합할 수 있습니다. 이 구조는 반복 가능하고 검증 가능한 정확성이 대규모로 필요할 때 빛납니다 — 정확히 AutoBe가 코드 생성에서 직면하는 상황입니다.

이것은 만능 해법이 아닙니다. 정확성이 타협 불가능하고 기계적으로 검증 가능한 도메인을 위한 해법입니다. 그 도메인에서는 대적할 것이 없습니다.

## 5. Qwen — 스몰 모델과 QA 엔지니어링

### 5.1. Function Calling 성능: 소형/중형 모델 최강

AutoBe의 전체 파이프라인은 function calling입니다. 모델이 좋은 산문을 쓰는지, 자연스러운 대화를 하는지는 무관합니다. 유일한 기준은 복잡한 JSON Schema를 얼마나 정확히 채우느냐입니다.

Qwen만이 오픈 웨이트 모델 중 function calling을 잘하는 것은 아닙니다. GLM, Kimi 등도 대형 스케일에서 강한 성능을 보입니다. 하지만 **소형/중형 스케일**에서 이 복잡성의 function calling을 처리할 수 있었던 것은 Qwen이 유일했습니다.

활성 파라미터 3B의 소형 MoE 모델도 tool choice를 지원하고, 10개 이상 변종의 재귀 유니온을 포함하는 복잡한 스키마를 처리합니다. AutoBe에게 이 소형/중형 성능이 결정적이었던 이유는 아래에서 계속됩니다.

### 5.2. R&D 비용: 사용자 vs 개발자

AutoBe를 **사용하는** 고객에게 모델 비용은 논점이 아닙니다. 가장 비싼 모델도 백엔드 개발자 한 명 고용하는 것보다 쌉니다.

AutoBe를 **개발하는** 우리에게는 다릅니다. 새로운 타입 설계나 검증 규칙을 추가할 때마다 전체 파이프라인을 처음부터 끝까지 실행해야 합니다. 수천 번의 생성-컴파일-피드백 사이클. 이 규모로 상용 모델을 사용하면 재정적 파국입니다.

로컬 모델이 R&D 사이클을 가능하게 합니다. 제한 없이, 비용 걱정 없이 실험합니다. 6.75%에서 100%까지의 여정에는 수백 번의 실험 사이클이 필요했습니다 — 모델이 로컬이었기에 가능했습니다.

### 5.3. 스몰 모델이 최고의 QA 엔지니어

대형 모델은 실수를 적게 합니다. 그것이 장점 — 이자 동시에 사각지대입니다.

우리가 미처 생각하지 못한 허점이 시스템에 있더라도, 대형 모델은 그 실패를 좀처럼 촉발하지 않습니다. 스키마의 모호한 부분을 "올바르게 추측해서" 통과합니다. 우리의 실수가 숨겨진 채로 남습니다.

소형 모델로 바꾸면 이야기가 달라집니다:

| 모델 | 활성 / 전체 | 성공률 | 발견한 것 |
|------|------------|--------|----------|
| `qwen3-30b-a3b-thinking` | 3B / 30B | ~10% | 근본적인 스키마 모호성, 누락된 필수 필드 |
| `qwen3-next-80b-a3b-instruct` | 3B / 80B | ~20% | 복잡한 중첩 관계의 미묘한 타입 불일치 |

10% 성공률이 가장 값진 결과였습니다. 모든 실패가 시스템의 허점을 가리켰고, 각각의 수정이 **모든 모델**을 위한 파이프라인을 강화했습니다.

AI는 확률적입니다. 대형 모델은 실수를 **덜 자주** 하지, **절대 안** 하는 것이 아닙니다. 소형 모델에서 표면화되는 에지 케이스는 대형 모델에서도 결국 발생합니다 — 단지 드물게. 프로덕션에서 "드물게"는 장애입니다.

**35B 모델조차 허점을 찾지 못할 만큼 시스템이 견고해지면, 어떤 모델이 실패할 확률은 사실상 0에 수렴합니다.**

소형 모델은 최고의 스트레스 테스터입니다. QA 엔지니어링 관점에서, 약한 모델이 오히려 더 강력한 검증 도구입니다.

### 5.4. 벤더 종속 없음

상용 API의 가격 변경, 모델 폐기, 요청 제한은 벤더의 재량입니다. 오늘 쓰는 모델이 내일 사라질 수 있습니다.

AutoBe의 function calling 스키마는 모델 중립적입니다. 모델별 프롬프트 트릭이 없습니다. JSON Schema와 타입 기반 검증은 산업 표준 — 모델이 바뀌어도 시스템은 그대로입니다.

### 5.5. 오픈 소스 + 오픈 웨이트: 선순환

AutoBe는 오픈 소스 (AGPL 3.0)입니다. Qwen은 오픈 웨이트입니다. 둘 다 오픈 생태계의 일부입니다.

이 조합이 수천 번의 실험을, 에지 케이스 발견을, 시스템 강화를 가능하게 했습니다. 상용 모델로는 이 규모의 실험이 재정적으로 불가능했을 것입니다.

오픈 생태계는 선순환을 만듭니다:
- AutoBe가 Qwen으로 시스템을 강화
- 강화된 시스템이 Qwen의 프로덕션 수준 활용 가능성을 증명
- Qwen의 향상이 AutoBe의 전반적 성능을 끌어올림
- AutoBe의 발견 (예: double-stringify 문제)이 Qwen의 개선에 기여 가능

## 6. 마무리

AutoBe는 4개 Qwen 모델 전부에서 100% 컴파일을 달성했습니다. 더 좋은 프롬프트가 아니라, 견고한 구조를 통해서.

세 가지입니다: 출력을 제약하는 타입 스키마, 결과를 검증하는 컴파일러, 오류를 교정하는 구조화된 피드백. 이 셋이 확률적 모델을 감싸는 결정론적 루프를 형성합니다.

이 패턴은 코드 생성에 한정되지 않습니다. 결정론적 검증기가 존재하는 모든 공학 도메인 — 반도체, 화학공정, 제어시스템 — 에 같은 구조를 구축할 수 있습니다.

타입으로 소통하면 오해가 없습니다. 스키마로 제약하면 분홍 코끼리가 없습니다. 결정론적 루프가 있으면 6.75%도 100%가 됩니다.

## 부록: 기술 심화

유니온 타입이 이 발표 전반에 등장합니다. `IJsonSchema`의 10개 변종 (2.5절), `IExpression`의 30개 이상 변종 (2.5절), Qwen 3.5의 double-stringify 문제 (3.4절), 타입 교정 (3.3절), validation feedback (3.5절). A.1–A.4절은 유니온 타입이 왜 핵심 도전인지를 탐구합니다. A.5절은 스키마 기반 파싱이 가능하게 하는 검증 너머의 능력을 탐구합니다.

### A.1. Discriminated Union이란?

유니온 타입은 "여러 종류 중 하나"를 나타냅니다. 결제 수단이 카드 또는 계좌이체일 수 있다면:

```typescript
type Payment =
  | { type: "card"; cardNumber: string; cvc: string }
  | { type: "bank_transfer"; bankCode: string; accountNumber: string }
```

**Discriminated** 유니온은 **판별자(discriminator) 필드** — 값으로 변종을 결정하는 단일 필드 — 를 가집니다. 여기서 `type`이 판별자입니다. `type`이 `"card"`면 `cardNumber`와 `cvc`가 있고, `"bank_transfer"`면 `bankCode`와 `accountNumber`가 있습니다. **하나의 판별자 값이 나머지 구조를 결정합니다.**

왜 중요할까요? LLM이 유니온 타입의 데이터를 생성하고 실수를 했을 때, 교정하려면 "어떤 변종을 의도했는가?"를 알아야 합니다. 판별자가 있으면 식별이 간단합니다 — 하나의 필드를 확인하면 변종을 알 수 있습니다. 판별자가 없으면 데이터의 형태에서 의도를 추론해야 합니다 — 더 어렵지만, 적절한 인프라가 있으면 가능합니다.

AutoBe의 `IJsonSchema` (10개 변종)과 `IExpression` (30개 이상 변종)은 모두 discriminated union이며, Typia가 구조적으로 변종을 식별하고 필드별 정밀 피드백을 생성하는 능력이 6.75% → 100%의 핵심 메커니즘입니다.

### A.2. Typia의 `x-discriminator` — `anyOf`에 지능을 더하다

JSON Schema는 `anyOf` (아무거나 매칭)와 `oneOf` (정확히 하나 매칭)를 유니온에 제공합니다. 둘 다 **"어떤 필드가 변종을 구분하는가"** — 를 담지 않습니다. 그저 "이 스키마들 중 하나에 매칭"이라고만 합니다.

OpenAPI v3.x에 `discriminator`가 있지만, `oneOf` 전용이고, 대부분의 LLM은 `oneOf`를 안정적으로 처리하지 못합니다.

Typia는 `x-discriminator`로 이를 해결합니다. LLM이 광범위하게 지원하는 `anyOf`를 사용하면서, 판별자 메타데이터를 부착합니다:

```json
{
  "anyOf": [
    { "type": "object", "properties": { "type": { "const": "card" }, "cardNumber": { ... } } },
    { "type": "object", "properties": { "type": { "const": "bank_transfer" }, "bankCode": { ... } } }
  ],
  "x-discriminator": {
    "propertyName": "type",
    "mapping": {
      "card": "#/$defs/CardPayment",
      "bank_transfer": "#/$defs/BankTransferPayment"
    }
  }
}
```

이것은 Typia의 내부 처리와는 별개의 목적입니다. Typia의 교정 로직과 검증 로직은 **구조 분석** — 속성명, 타입, 형태를 각 변종의 스키마와 매칭 — 으로 올바른 변종을 식별합니다. 판별자 유무와 무관하게 동작합니다.

`x-discriminator`는 **LLM을 위한** 것입니다. 모델에게 "`type` 필드로 변종을 선택하라"고 알려주어, 애초에 구조적으로 모호한 데이터가 생성될 확률을 줄입니다.

둘이 함께 작동합니다:

1. **`x-discriminator`가 소스에서 오류를 줄임** — LLM이 힌트를 읽고 더 명확한 데이터를 생성
2. **구조 분석이 나머지를 처리** — `parse()`가 변종을 식별하고 변종별 타입 교정을 적용 (Qwen 3.5의 double-stringify 해제 포함). `validate()`가 변종을 식별하고 필드별 정밀 오류를 생성 — "10개 변종 중 아무것도 매칭 안 됨"이 아니라, "card 변종의 cardNumber는 string이어야 하는데 number를 줬습니다"

**`x-discriminator`가 LLM을 더 정확하게 만듭니다. 구조 분석이 시스템을 견고하게 만듭니다.** 이것이 유니온 타입에서 교정과 검증이 안정적으로 동작하는 이유입니다.

### A.3. 세상은 재귀적 유니온으로 이루어져 있다

공학은 **계층적 분해** — 큰 시스템을 작은 부분으로, 그 부분을 더 작은 부분으로 쪼개는 것 — 로 복잡성을 관리합니다. 칩은 블록이고, 블록은 서브블록입니다. 플랜트는 섹션이고, 섹션은 유닛입니다. 건물은 층이고, 층은 방입니다. 이 분해는 트리입니다. 각 수준에서 부분들은 서로 다른 종류를 가집니다 — 블록은 logic, memory, IO일 수 있고, 유닛은 reactor, distillation column, heat exchanger일 수 있습니다. 트리의 노드에 종류가 생기는 순간, 그것은 **재귀적 유니온 타입**이 됩니다.

4장의 도메인들이 모두 이렇습니다:

- 반도체: `IBlock` → `sub_blocks: IBlock[]` (칩 → 블록 → 서브블록)
- 화학공정: 플랜트 → 섹션 → 유닛 → 서브유닛 (재귀적 공정 계층)
- 인테리어: 건물 → 층 → 방 → 구역 (재귀적 공간 분해)
- 제어시스템: 캐스케이드 제어 — 외부 루프의 출력이 내부 루프의 설정값 (재귀적 중첩)

AutoBe의 `IJsonSchema` (10개 변종)과 `IExpression` (30개 이상 변종)과 구조적으로 동일합니다. 모두 AST — 추상 구문 트리 — 입니다. **계층적 분해는 엔지니어가 복잡성을 관리하는 방식이고, 계층적 분해는 재귀적 유니온 타입을 생산합니다.** 모든 결정론적 공학 도메인이 이 구조를 공유합니다.

결정론적 검증기가 있는 모든 도메인에 같은 구조가 적용되고, 그 도메인들이 모두 재귀적 유니온 데이터 구조를 공유한다면, **유니온 타입을 정복하는 것이 이 구조를 구축하기 위한 전제 조건**입니다.

교정이 유니온에서 동작하지 않으면 Qwen 3.5의 double-stringify가 칩 설계에서도 나타납니다. 검증 피드백이 유니온에서 동작하지 않으면 "30개 변종 중 아무것도 매칭 안 됨"으로는 수렴이 불가능합니다. 의도된 변종을 식별하지 못하면 교정이 불가능합니다.

Typia의 구조적 변종 식별, 스키마 기반 교정, 필드별 정밀 검증이 이 보편적 구조를 위한 해법입니다. AutoBe의 6.75% → 100%는 코드 생성의 성과만이 아닙니다. **재귀적 유니온이라는 보편 구조에서의 신뢰성을 확립한 것 — 이 구조를 공유하는 모든 도메인으로 이전 가능한 성과입니다.**

### A.4. 왜 Zod가 아닌가?

Zod는 TypeScript에서 가장 인기 있는 런타임 검증 라이브러리입니다. "왜 Zod가 아닌가?"는 자주 받는 질문입니다.

AutoBe 규모의 30개 이상 변종 재귀 discriminated union을 Zod로 정의하면 어떻게 되는지 봅시다:

```typescript
const ExpressionSchema: z.ZodType<IExpression> = z.lazy(() =>
  z.discriminatedUnion("type", [
    z.object({ type: z.literal("booleanLiteral"), value: z.boolean() }),
    z.object({
      type: z.literal("callExpression"),
      expression: ExpressionSchema,         // 순환 참조
      arguments: z.array(ExpressionSchema),  // 순환 참조
    }),
    // ... 28개 더
  ])
);
```

세 가지 문제가 있습니다.

**첫째, TypeScript 타입과 Zod 스키마를 별도로 정의해야 합니다.**

Zod 문서가 이를 명시합니다: "you can define a recursive schema in Zod, but because of a limitation of TypeScript, their type can't be statically inferred." `z.lazy()`를 쓰면 `z.infer`가 작동하지 않으므로, TypeScript 인터페이스를 별도로 정의하고 `z.ZodType<T>`로 연결합니다:

```typescript
// 1. TypeScript 타입을 먼저 정의
type IExpression =
  | { type: "booleanLiteral"; value: boolean }
  | { type: "callExpression"; expression: IExpression; arguments: IExpression[] }
  | { type: "binaryExpression"; left: IExpression; operator: string; right: IExpression }
  // ... 27개 더

// 2. Zod 스키마를 별도로 정의하고 수동으로 타입 힌트 연결
const ExpressionSchema: z.ZodType<IExpression> = z.lazy(() =>
  z.discriminatedUnion("type", [
    z.object({ type: z.literal("booleanLiteral"), value: z.boolean() }),
    z.object({ type: z.literal("callExpression"), expression: ExpressionSchema, arguments: z.array(ExpressionSchema) }),
    z.object({ type: z.literal("binaryExpression"), left: ExpressionSchema, operator: z.string(), right: ExpressionSchema }),
    // ... 27개 더
  ])
);
```

30개 이상 변종의 재귀 유니온에서 이 이중 정의는 수백 줄에 달합니다. 시간이 지나면 둘이 어긋나고, 아무것도 그 불일치를 잡아주지 않습니다.

**둘째, 이중 정의를 감수해도 컴파일이 안 됩니다.**

재귀 유니온의 깊이가 증가하면 TypeScript의 제네릭 인스턴스화 한계에 부딪힙니다:

> TS2589: Type instantiation is excessively deep and possibly infinite.

네이티브 TypeScript 타입에서 재귀 참조는 **이름 조회(name lookup)** — 같은 정의를 가리키는 포인터입니다. 30개 변종이 `IExpression`을 참조하면? 30번의 포인터 조회. **O(N) — 선형.**

Zod에서 `z.discriminatedUnion`은 깊이 중첩된 제네릭입니다. TypeScript가 각 변종의 출력 타입을 Zod의 조건부 타입을 통해 **구조적으로 확장**해야 합니다. `z.lazy()`가 전체 유니온에 대한 재진입을 강제합니다 — N 변종 × K 재귀 필드, 각각이 또 다른 확장을 촉발합니다. N=30, K=2, 깊이 3이면 216,000회의 타입 해석. **O((N·K)^d) — 지수적.**

이것은 Zod 이슈 트래커에서 가장 반복적으로 보고되는 오류입니다. [#577](https://github.com/colinhacks/zod/issues/577), [#5064](https://github.com/colinhacks/zod/issues/5064), [#5256](https://github.com/colinhacks/zod/issues/5256) — 모두 재귀 스키마, 모두 TS2589, Zod v4에서도 미해결. [Discussion #1459](https://github.com/colinhacks/zod/discussions/1459)는 재귀조차 아닌 복잡한 discriminated union에서 같은 오류를 보여줍니다 — 제네릭 확장만으로도 비용이 충분합니다.

실질적인 결과는 IDE까지 미칩니다. TypeScript 언어 서버가 자동완성과 호버 타입에 같은 타입 체커를 돌립니다. 30개 이상 변종 재귀 Zod 스키마가 같은 지수적 확장을 촉발 — 메모리가 기가바이트 단위로 치솟고, 스키마 파일뿐 아니라 그것을 임포트하는 모든 파일에서 IDE가 멈춥니다.

**셋째, 이 모든 것을 감수해도 피드백 루프를 구축할 수 없습니다.**

이것이 결정적인 문제입니다.

유니온 타입에서 검증이 실패하면, Zod는 "어떤 변종을 의도했는지" 판별하지 못합니다. 10개 변종 유니온에서 모든 변종에 대한 오류가 쏟아지거나 ([#792](https://github.com/colinhacks/zod/issues/792)), 판별자 불일치 시 다른 필드 오류가 조용히 숨겨지거나 ([#2202](https://github.com/colinhacks/zod/issues/2202)). Zod v4에서는 더 퇴보했습니다: 판별자 불일치 시 빈 오류 배열과 "No matching discriminator"를 반환 ([#4909](https://github.com/colinhacks/zod/issues/4909), [#5670](https://github.com/colinhacks/zod/issues/5670)).

LLM 입장에서: `callExpression` 변종을 의도했지만 `arguments` 필드의 타입을 틀렸다면, "arguments는 IExpression 배열이어야 하는데 string을 줬습니다"라는 피드백이 필요합니다. Zod가 주는 것은 "10개 변종 중 아무것도 매칭 안 됨." 무엇을 고쳐야 하는지 알려주지 않는 피드백은 피드백이 아닙니다. 정밀한 피드백 없이는 루프가 수렴하지 않습니다.

Typia는 데이터의 형태를 분석하여 의도된 변종을 구조적으로 식별한 뒤, 그 변종의 스키마에 대해 필드별 정밀 오류를 생성합니다. 이것이 피드백 루프가 작동하기 위한 전제 조건이며, Zod에는 이 메커니즘이 완전히 부재합니다.

**Zod: 이중 정의, 컴파일 실패, 피드백 루프 불가. Zod 위에서는 이 구조를 구축할 수 없습니다.**

Typia는 하나의 인터페이스만 있으면 됩니다:

```typescript
const result = typia.validate<AutoBeTest.IExpression>(llmOutput);
```

컴파일러 수준에서 동작합니다. 별도 스키마 없음, 제네릭 깊이 한계 없음, 불완전한 오류 없음.

### A.5. 토큰 한계를 넘어: 점진적 구조화 출력

Function calling에는 말하지 않는 제약이 있습니다: **전체 JSON이 단일 응답에 들어와야 합니다.** 모델의 최대 출력이 32K 토큰인데 대상 JSON이 100K 토큰이면, 출력이 JSON 중간에서 잘립니다. `JSON.parse()`에게 잘린 JSON은 실패한 JSON입니다. 전체 생성이 낭비됩니다.

Typia의 스키마 기반 lenient parsing이 이 구도를 바꿉니다. `parse()`가 닫히지 않은 괄호를 자동으로 닫고, 불완전한 값을 완성하고, 타입 교정을 재귀적으로 적용하므로 — 잘린 JSON이 실패가 아닙니다. `DeepPartial<T>`: 완성된 필드는 유효하고, 누락된 필드는 스키마로 식별 가능한 타입 객체입니다.

```
Turn 1: LLM이 32K 토큰 생성 → JSON 중간에서 잘림
         → Typia parse() → DeepPartial<T>
         → 스키마 diff: "이 필드들이 아직 없습니다"

Turn 2: "나머지 필드를 채워주세요" + 이전 DeepPartial<T>
         → LLM이 다음 청크 생성 → Typia parse()
         → DeepPartial<T> 갱신, 완성된 하위 트리에 validate()

Turn N: → 모든 필드 존재 → validate() 통과 → T
```

각 턴에서 `parse()`가 잘린 출력을 복구하고 타입을 교정하며, `validate()`가 완성된 하위 트리에서 먼저 실행될 수 있습니다. 오류가 마지막이 아닌 점진적으로 표면화됩니다.

이것은 구조화된 출력에 적용된 증분 컴파일입니다. 기존 function calling은 잘린 출력을 버리고 처음부터 재시도합니다. Typia의 접근은 모든 유효한 필드를 재사용하고, LLM에게 누락된 부분만 채우라고 요청합니다.

**Function calling의 출력 크기가 더 이상 `max_output_tokens`에 제한되지 않습니다.** 200K 토큰의 JSON을 여러 턴에 걸쳐 점진적으로 구축할 수 있으며, 매 단계마다 타입 안전성이 유지됩니다. 스키마가 무엇을 가지고 있고 무엇이 필요한지 알려주고, lenient parser가 아무것도 낭비되지 않게 보장합니다.

구조화된 출력을 점진적으로 구축할 수 있게 되면, function calling이 생산할 수 있는 것의 상한이 사라집니다.
