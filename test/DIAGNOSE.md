# AutoBE 벤치마크 컴파일 오류 진단

너는 AutoBE 벤치마크 결과에 대한 전문 진단관이다. `test/debug.log.md`의 컴파일 에러 로그와 `test/results/`의 생성된 프로젝트 소스 코드를 정밀 분석하여, 모든 오류의 근본 원인을 추적하고 구체적 해결안을 도출하라.

---

## 1. 운영 원칙

- **무한 비용·무한 시간**: 1시간이든 2시간이든, 완벽할 때까지 조사하고 탐구한다.
- **전수 조사**: 오류를 하나라도 빠뜨리지 않는다. 샘플링이 아닌 전수 분석이다.
- **Bottom-Up**: 개별 프로젝트를 낱낱이 해부한 다음에야 전체를 논한다. 절대 top-down으로 분류부터 하지 않는다.
- **자기 비판**: 모든 결론에 대해 반증을 시도한다. 확증 편향을 경계한다.
- **모델 내 해결**: "더 큰 모델을 쓰면 된다"는 답은 금지. 현재 주어진 모델 내에서 해법을 찾는다.
- **열린 사고**: 프롬프트 수정, validation 로직 변경, 아키텍처 혁신 — 어떤 해법이든 제약 없이 탐색한다. 단 해법 탐색의 출발점은 항상 `packages/agent/prompts/`의 시스템 프롬프트 수정이고, 거기서부터 더 넓은 방안으로 확장한다.
- **gitignore 준수**: node_modules, build, .env 등 gitignore된 파일은 절대 탐색하지 않는다.

## 2. 입력물

### 2.1. test/debug.log.md

`test/src/archive/debug.ts`가 생성하는 컴파일 에러 로그. 포맷:

```markdown
## `{vendor}/{model}` - `{project}`

Total N compile errors.

### Location

\`\`\`bash
code {path-to-realize-folder}
\`\`\`

### `{error-file-path}`
- {error-message-1}
- {error-message-2}
...
```

여기서 project는 `reddit`, `shopping`, `erp` 같은 벤치마크 예제 프로젝트명이다.

### 2.2. test/results/ 디렉토리

```
test/results/{vendor}/{model}/{project}/realize/
├── prisma/schema/               # Prisma 스키마 (.prisma 파일들)
├── src/
│   ├── api/structures/          # API 응답 DTO 타입 정의 (.ts)
│   ├── providers/               # ★ 생성된 비즈니스 로직 코드 (오류 발생 주요 지점)
│   ├── transformers/            # ★ 생성된 데이터 변환 코드 (오류 발생 주요 지점)
│   ├── collectors/              # ★ 생성된 데이터 수집 코드 (오류 발생 주요 지점)
│   ├── controllers/             # 생성된 컨트롤러
│   └── ...
└── ...
```

## 3. 실행 절차

### 3.1. Phase 0: 입력물 확인

`test/debug.log.md`를 읽고, `test/results/` 폴더의 디렉토리 트리를 확인하라. 어떤 벤더/모델/프로젝트 조합이 존재하는지 전체 목록을 파악한다.

### 3.2. Phase 1: 실패 프로젝트 목록 확정

`test/debug.log.md`를 전수 읽어라 (수백KB여도 전부). 각 `## {vendor}/{model} - {project}` 섹션에서:

- 실패한 프로젝트 전체 목록을 추출한다
- 각 프로젝트의 오류 파일 수와 오류 메시지 수를 집계한다
- 요약 테이블을 만든다

### 3.3. Phase 2: 프로젝트별 정밀 해부 ★

**이 단계가 전체 진단의 80%이다.** 한 프로젝트도 빠짐없이, 모든 오류 파일을 하나하나 해부한다.

오류가 많은 모델부터 시작한다. 작은 모델은 다양한 오류 패턴을 보여주어 분류에 유리하고, 큰 모델의 희소한 오류는 "프롬프트로 쉽게 안 고쳐지는" 근본적 이슈를 가리킨다.

**각 오류 파일에 대해 아래 7단 분석을 빠짐없이 수행하라:**

#### 3.3.1. 컴파일 에러 메시지

`test/debug.log.md`에서 해당 파일의 에러 메시지를 그대로 인용한다.

#### 3.3.2. DB 스키마 (Prisma)

`test/results/{vendor}/{model}/{project}/realize/prisma/schema/`에서 오류 관련 Prisma 모델을 찾아 읽는다.

- 해당 모델의 **컬럼 정의**와 **릴레이션 정의** (belonged relations, has relations) 전문을 인용
- 오류가 릴레이션 관련이면, 연관 모델의 릴레이션 정의도 함께 인용
- 핵심 포인트를 짚는다 (예: "이 릴레이션의 실제 프로퍼티명은 `profileSnapshots`이지 `profile`이 아니다")

#### 3.3.3. API 응답 DTO 스펙

`test/results/{vendor}/{model}/{project}/realize/src/api/structures/`에서 Transformer/Provider가 생성해야 하는 대상 타입을 찾아 읽는다.

- 해당 DTO 인터페이스 전문 (또는 핵심 부분) 인용
- 필수/nullable 필드, 중첩 객체 구조, 계산 필드 여부 명시
- DB 스키마와 DTO 사이의 불일치가 있다면 여기서 짚는다

#### 3.3.4. 문제의 코드

오류가 발생한 생성된 TypeScript 파일을 `realize/src/` 하위(providers/, transformers/, collectors/)에서 찾아 전문 읽기.

- 전체 코드를 인용하되, 오류 발생 지점에 인라인 주석 표시 (예: `// <-- 오류: author 프로퍼티 접근 불가`)

#### 3.3.5. 오류 원인 분석

**3단 추적**으로 분석한다:

- **무엇이 잘못되었는가**: 오류의 직접적 원인 (예: select에 릴레이션 미포함)
- **왜 이런 코드가 생성되었는가**: LLM이 왜 이런 실수를 했는지 추정 (예: FK 컬럼명에서 릴레이션명을 추측)
- **설계(DB/API) 수준 문제인가, 구현(코드 생성) 수준 문제인가**: 명확히 판정
- 교정 루프(self-healing loop)에서 왜 고쳐지지 않았는지도 분석

#### 3.3.6. 올바른 코드 (수정 예시)

가능한 경우, 올바르게 작동하는 코드 예시를 제시한다.

#### 3.3.7. 권고 조치사항

해당 오류에 대한 간결한 제안:

- **프롬프트 수준**: 어떤 프롬프트(`packages/agent/prompts/`)에 어떤 규칙을 추가해야 하는지
- **교정 루프 수준**: 교정 프롬프트(CORRECT 계열)에 추가할 가이드
- **설계 수준**: Interface/Database 단계에서 사전 방지할 방법
- 필요하다면 validation 로직이나 아키텍처 변경도 제언

### 3.4. Phase 3: 전체 취합

Phase 2의 모든 프로젝트별 분석을 취합하여 다음을 생성한다:

#### 3.4.1. 오류 분류 체계

Phase 2에서 발견된 모든 오류 패턴을 클러스터링하여 클래스 A, B, C, ...로 명명. 각 클래스에 대해:

- 증상 (TS 에러 코드 + 메시지 패턴)
- 메커니즘 (왜 발생하는지)
- 근본 원인 (프롬프트/설계/모델 한계)
- 빈도 (전체 오류의 몇 %)
- 대표 사례 (어떤 모델/프로젝트에서 관찰되었는지)

#### 3.4.2. 오류 히트맵

모델 × 프로젝트 × 오류 클래스 매트릭스. 프로젝트별 평균 오류 수, 모델별 실패 시그니처.

#### 3.4.3. 프로젝트별 설계 갭 분석

프로젝트(reddit, shopping, erp 등)마다:

- 엔티티 계층 구조
- DB 스키마 ↔ API DTO 사이의 설계 갭 테이블
- 판정 (설계 갭 밀도)
- 수정 우선순위
- 프로젝트 간 공통 패턴 및 고유 패턴
- 복잡도 순위

### 3.5. Phase 4: 근본 원인 심화 탐구

Phase 2~3에서 발견한 오류 클래스 각각에 대해, **증거가 이끄는 곳이면 어디든** AutoBE 소스 코드를 파고든다. 미리 정해진 디렉토리 목록만 보지 말고, Phase 2의 개별 분석에서 드러난 단서를 추적하여 원인이 있는 곳까지 따라가라.

탐구해야 할 질문들:

- **프롬프트**: `packages/agent/prompts/`의 88개 파일 중, 이 오류 클래스와 관련된 프롬프트는 무엇인가? 그 프롬프트의 어느 부분이 부족해서 LLM이 이런 실수를 하는가? Realize 단계뿐 아니라, 상류(Database, Interface 단계)에서 정보가 유실되거나 잘못 전달되는 지점은 없는가?
- **오케스트레이션**: 교정 루프(self-healing loop)가 왜 이 오류를 고치지 못했는가? 오류 메시지가 LLM에게 어떤 형태로 전달되는가? 히스토리 트랜스포머가 핵심 정보를 잘라내고 있지는 않은가?
- **컴파일러**: 진단 메시지가 LLM이 문제를 이해하기에 충분한가? validation logic이 잘못된 코드를 사전에 걸러낼 수 있었는데 놓치고 있는 것은 없는가?
- **타입 시스템 / 기반 라이브러리**: Prisma, NestIA, Typia 등의 동작 방식이 LLM의 추론에 함정을 만들고 있지는 않은가?
- **정보 전달 체인**: DB 스키마 → Interface 설계 → Realize 구현으로 이어지는 파이프라인에서, 릴레이션명·nullable 여부·계산 필드 구분 등의 정보가 어디에서 손실되는가?

탐색 범위에 제한은 없다. `packages/agent/`, `packages/compiler/`, `packages/interface/`, `packages/rpc/` 등 gitignore되지 않은 모든 소스 코드가 대상이다.

#### 3.5.1. 업계 사례 연구 (웹 검색)

다른 코딩 에이전트들(Claude Code, Cursor, Devin, Copilot Workspace 등)의 "컴파일러 피드백 → LLM 재생성" 루프 구현 사례. 오류 트리아지, 점진적 수정 등의 최신 기법. **"더 큰 모델을 쓰라"는 제안은 금지.**

### 3.6. Phase 5: 자기 비판 및 교차 검증

Phase 2~4의 모든 결론에 대해 반증을 시도한다.

- "프롬프트만 고치면 된다" → 확률론적 LLM 특성상 프롬프트 몇 줄로 100% 해결되는가?
- "아키텍처를 바꿔야 한다" → 최소 침습적 해법은 정말 없는가?
- 각 해법에 대해 **비용(구현 난이도) × 효과(해결 오류 비율)** 매트릭스 작성
- 정직한 한계 기술: 현재 모델로 해결 불가능한 영역은 명시

### 3.7. Phase 6: 해결안 도출

#### 3.7.1. 프롬프트 개정안

각 프롬프트 파일에 삽입할 구체적 텍스트 블록. 바로 통합 가능한 수준으로 작성. 삽입 위치, 근거 오류(어떤 모델/프로젝트의 어떤 에러가 근거인지), 기대 효과, 우선순위(P0~P3).

#### 3.7.2. Validation/Orchestration 로직 개선안

교정 루프 개선, 진단 메시지 개선, 기계적 사전 교정 자동화, 정보 전달 체인 보강.

#### 3.7.3. 아키텍처 혁신안 (필요 시)

새로운 에이전트 패턴, 업계 사례 영감, 파이프라인 구조 변경.

### 3.8. Phase 7: 최종 자기 검토

- 모든 보고서를 처음부터 끝까지 재독
- **누락 대조**: debug.log.md의 모든 오류가 providers/ 진단서에 빠짐없이 등장하는지 확인
- 해결안의 실현 가능성 최종 검증
- 보고서 간 상호 참조 정합성 확인

## 4. 출력물

모든 결과는 `test/diagnoses/`에 작성한다.

### 4.1. 필수 산출물 (구조 고정)

아래 두 가지는 유저가 직접 읽는 문서이다. 반드시 지정된 구조를 따른다.

#### 4.1.1. 모델별 상세 진단서 — `providers/{model-name}.md`

Phase 2의 산출물. 모델 하나당 파일 하나. 구조:

```markdown
# {model-name} 컴파일 오류 상세 진단서

> **모델**: {model-name}
> **프로바이더**: {vendor}
> **프로젝트**: {실패한 프로젝트 목록}
> **총 오류 파일 수**: N개
> **총 컴파일 오류 수**: N개

---

## 프로젝트: {project-name}

### 오류 파일 1: `{filename}.ts`

#### 1. 컴파일 에러 메시지
#### 2. DB 스키마 (Prisma)
#### 3. API 응답 DTO 스펙
#### 4. 문제의 코드
#### 5. 오류 원인 분석
#### 6. 올바른 코드 (수정 예시)
#### 7. 권고 조치사항

### 오류 파일 2: ...

## 프로젝트: {project-name-2}
...
```

#### 4.1.2. 종합 제안서 — `README.md`

Phase 3~7의 최종 산출물. 오류 분류 체계, 히트맵, 프롬프트 개정안, 로직 개선안, 아키텍처 혁신안 등 모든 분석 결과와 해결안을 한 문서에 종합한다.

### 4.2. 부속 문서 (재량)

위 두 필수 산출물 외에, 분석 과정에서 필요한 부속 문서(히트맵, 프로젝트별 설계 갭, 프롬프트 갭 분석, 개정 문안 등)는 자유롭게 파일을 나누고 정리하라. 파일명, 구조, 개수 모두 재량이다.

---

## 5. 실행하라

Phase 0부터 Phase 7까지 순서대로 실행하라. `test/diagnoses/` 폴더에 결과를 작성하라. 시간과 비용에 제한은 없다. 완벽을 기하라.
