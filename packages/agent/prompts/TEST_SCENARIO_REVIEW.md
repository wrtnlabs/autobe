## Input Materials

You will receive:
1. An array of API operation objects with their specifications, descriptions, and parameters  
2. Complete **interface schema definitions** for all request/response bodies referenced by the operations (from `document.components.schemas`)
3. Include/exclude lists for targeted test generation
4. Candidate dependencies mapping showing which operations require which IDs

The **interface schemas** represent the TypeScript interface definitions for API request and response bodies. These schemas define:
- Object types like `IUser`, `IProduct`, `IOrder` 
- Request DTOs like `IUser.ICreate`, `IProduct.IUpdate`
- Response DTOs like `IUser.ISummary`, `IPageIProduct`
- Property types, required fields, and validation constraints
- References between different schema types

### 1.2. Interface Schema and API Operation Validation

**MANDATORY: Complete API Operation Coverage Analysis**

After confirming endpoint existence, you MUST perform comprehensive validation that:

1. **Complete Dependency Chain Validation**: Each scenario has all prerequisite operations needed for successful execution
2. **Interface Schema Property Accuracy**: All referenced properties exist in the actual interface schema definitions
3. **Data Flow Consistency**: IDs and data flow logically from response interface schemas to request interface schemas
4. **Authentication Requirements Fulfillment**: All authentication operations use only available auth APIs

### 1.3. Dependency Chain Analysis

**CRITICAL: Recursive Dependency Resolution Verification**

For every scenario, you MUST verify:

1. **Complete Dependency Tracing**: Every required ID has been traced back to its source operation
2. **Recursive Dependencies Analysis**: For each endpoint in the current dependencies array, check if IT also requires IDs from the Candidate Dependencies table and add those provider operations
3. **Execution Order Validation with User Context**: Dependencies are ordered correctly based on BOTH data flow requirements AND user context switching logic
4. **No Missing Links**: No gaps exist in the dependency chain from authentication to target operation
5. **Candidate Dependencies Compliance**: All IDs mentioned in the Candidate Dependencies table are properly addressed for ALL operations (target + dependencies)
6. **Business Logic Sequence with Authentication Flow**: The order of operations makes business sense, follows realistic workflows, AND ensures proper user context is established before each protected operation

**Comprehensive Dependency Ordering Process:**
```
Step 1: Identify ALL required operations (target + recursive dependencies)
Step 2: Map each operation to its authorizationRole requirement
Step 3: Group operations by required user context
Step 4: Order groups by business logic (admin setup → user actions → admin approval)
Step 5: Insert authentication operations (join/login) at context switch points
Step 6: Validate data flow works with the authentication-aware ordering
```

**Example of Complete Dependency Analysis:**
```
Target: PUT /orders/{orderId}/items/{itemId}
Current dependencies: [POST /orders/{orderId}/items]

Step 1 - Recursive dependency resolution:
- POST /orders/{orderId}/items requires orderId + productId
- POST /orders requires customerId, POST /products requires categoryId
- All required operations: [POST /categories, POST /products, POST /customers, POST /orders, POST /orders/{orderId}/items]

Step 2 - AuthorizationRole mapping:
- POST /categories (authorizationRole: "admin")
- POST /products (authorizationRole: "seller") 
- POST /customers (authorizationRole: null)
- POST /orders (authorizationRole: "customer")
- POST /orders/{orderId}/items (authorizationRole: "customer")
- PUT /orders/{orderId}/items/{itemId} (authorizationRole: "admin")

Step 3 - Final ordered dependencies with user context:
1. admin/join → establish admin context
2. POST /categories → admin creates category
3. seller/join → switch to seller context
4. POST /products → seller creates product  
5. POST /customers → public operation (no auth needed)
6. customer/join → switch to customer context
7. POST /orders → customer creates order
8. POST /orders/{orderId}/items → customer adds items
9. admin/login → switch back to admin context (created earlier)
10. Target: PUT /orders/{orderId}/items/{itemId} → admin updates item
```

### 1.4. User Context Management Review

**ABSOLUTE REQUIREMENT: Authentication Flow Validation**

You MUST rigorously review authentication patterns:

**✅ CORRECT Authentication Patterns:**
- `join` operations for creating NEW users with specific roles
- `login` operations ONLY for switching back to PREVIOUSLY CREATED users
- No `login` immediately after `join` for the same role
- Each unique role gets exactly ONE `join` operation per scenario
- Context switching serves clear business purposes

**❌ FORBIDDEN Authentication Patterns (MUST BE REMOVED):**
- `join` + `login` immediately for same role
- Multiple `join` operations for same role without valid context switching need
- `login` before any `join` for that role
- Any duplicate authentication operations in dependencies array
- Authentication operations that don't exist in available APIs

**CRITICAL: AuthorizationRole-Based Context Analysis**

You MUST analyze each operation's `authorizationRole` field to determine optimal authentication flow:

1. **Role Requirement Mapping**: For each operation in the dependency chain, identify its required `authorizationRole`
2. **Minimal Authentication Strategy**: Create users only for roles that are actually needed
3. **Context Switch Justification**: Only switch between roles when different `authorizationRole` values require it
4. **Logical Role Sequence**: Order role creation based on business workflow (e.g., admin creates resources first, then users consume them)
5. **Dynamic Authentication Flow Optimization**: Analyze the dependencies array, find each endpoint's corresponding Operation and its authorizationRole, then reorder/modify/remove login/join APIs to ensure proper user context switching

**Authentication Flow Optimization Process:**
```
Step 1: Map each dependency endpoint to its Operation's authorizationRole
Step 2: Identify required user context switches
Step 3: Remove redundant join/login operations
Step 4: Reorder authentication operations for logical flow
Step 5: Ensure each protected operation has proper auth context
```

**Example of AuthorizationRole Analysis:**
```
Dependencies: [POST /admin/categories, POST /user/orders, PUT /admin/orders/{orderId}/approve]
Operation Analysis:
- POST /admin/categories (authorizationRole: "admin")
- POST /user/orders (authorizationRole: "user") 
- PUT /admin/orders/{orderId}/approve (authorizationRole: "admin")

Optimized flow:
1. admin/join → establish admin context
2. POST /admin/categories → use admin context
3. user/join → switch to user context  
4. POST /user/orders → use user context
5. admin/login → switch back to admin context (created earlier)
6. PUT /admin/orders/{orderId}/approve → use admin context
```
