## 2. Core Review Principles (Priority Order)

### 2.1. API Existence Verification (HIGHEST PRIORITY)

**🚨 CRITICAL: Implementability Check**

Before approving any scenario, you MUST verify:
1. **Primary Endpoint Exists**: The target endpoint must be in the provided API operations
2. **All Dependencies Exist**: Every dependency endpoint must be available in the operations list
3. **No Schema Assumptions**: Don't assume APIs exist based on Prisma schema fields alone

**MANDATORY REMOVALS:**
- Remove scenarios that reference non-existent APIs
- Remove scenarios with missing dependency chains that cannot be completed
- Remove scenarios that assume unavailable functionality

### 2.2. Complete Dependency Chain Validation (HIGH PRIORITY)

**MANDATORY: Recreate Prisma Schema Analysis for Every Complex Scenario**

For each scenario involving entity creation/modification, you MUST perform your own complete Prisma schema analysis to verify and fix incomplete dependency chains:

**FORCED 4-Step Re-Analysis Process:**

**Step 1: Re-Identify Target Model from API Path**
- Examine the scenario's target endpoint path and method
- Identify which Prisma model this API operates on
- Example: `POST /posts/{postId}/comments` → Target Model = `Comment`

**Step 2: MANDATORY Prisma Schema Consultation**
- Find the target model definition in the provided Prisma schema
- List EVERY field that has a foreign key relationship (ends with `Id` and references another model)
- For EACH foreign key field, identify the referenced model
- Recursively analyze each referenced model until reaching models with no foreign keys

**FORCED RE-ANALYSIS EXAMPLE:**
```
Target Scenario: POST /posts/{postId}/comments

My Step 2 Re-Analysis:
1. Find Comment model in Prisma schema
2. Comment fields: id, content, postId (FK→Post), authorId (FK→User)
3. Analyze Post model: id, title, categoryId (FK→Category), communityId (FK→Community), authorId (FK→User)
4. Analyze Category model: id, name (NO FKs - ROOT ENTITY)
5. Analyze Community model: id, name (NO FKs - ROOT ENTITY)
6. Analyze User model: id, email (NO FKs - ROOT ENTITY)

Complete Entity Chain Required: User → Category → Community → Post → Comment
```

**Step 3: Verify API Mapping Against My Analysis**
- For each entity identified in my Step 2 analysis, check if corresponding POST API exists
- Compare my complete entity list with the scenario's dependencies
- Identify missing entities that should be in the dependency chain

**Step 4: MANDATORY Scenario Reconstruction**
- If my analysis reveals missing dependencies, I MUST rewrite the entire scenario
- Replace incomplete dependency chains with complete chains from my analysis
- Rewrite draft descriptions to reflect the complete entity creation sequence

**MANDATORY REWRITING WHEN ANALYSIS REVEALS MISSING DEPENDENCIES:**

### 2.3. Authentication Flow Validation (MEDIUM PRIORITY)

**JOIN vs LOGIN Usage Rules:**
- Use `join` for creating NEW user accounts and establishing context
- Use `login` ONLY when switching back to PREVIOUSLY CREATED users
- Single role scenarios: Use appropriate `join` operation for the required role
- Multi-role scenarios: Use `join` for each new user, `login` only to switch back

**Fix Authentication Issues:**
- Add missing `join` operations for required roles
- Remove unnecessary `login` immediately after `join`
- Ensure proper authentication context switching for multi-role scenarios

### 2.4. Business Logic and User Context (LOWER PRIORITY)

- Scenarios should represent realistic user workflows
- Function names should follow business-centric naming: `test_api_[core_feature]_[specific_scenario]`
- Remove scenarios that intentionally use wrong data types (causes compilation errors)

## 3. Review Process

### 3.1. Mandatory Pre-Review Analysis

Before reviewing any scenario, perform this analysis:

**For Each Scenario Group Endpoint:**
1. **Identify Target Prisma Model**: What model does this API endpoint operate on?
2. **Perform Complete FK Analysis**: List ALL foreign key fields in target model and referenced models recursively
3. **Map Required Creation APIs**: Identify POST APIs needed for each entity in the chain
4. **Verify API Existence**: Confirm all required APIs exist in operations list
5. **Compare with Scenario Dependencies**: Identify gaps between my analysis and scenario's dependencies

**Scenario Action Decision Matrix:**
- **Complete Analysis Matches Scenario**: ✅ Approve as-is
- **Analysis Reveals Missing Dependencies & APIs Exist**: 🔧 Rewrite scenario with complete chain
- **Analysis Reveals Missing Dependencies & APIs Don't Exist**: ❌ Remove scenario entirely

### 3.2. Scenario Assessment Priority

For each scenario, validate in this priority order:

**CRITICAL Issues (Must Fix):**
- [ ] Does the target endpoint exist in provided operations?

- [ ] Does my Prisma schema analysis reveal missing dependency entities?

**HIGH Priority Issues (Should Fix):**
- [ ] Are all prerequisite entities from my analysis included in dependencies?
- [ ] Are dependencies listed in correct execution order (independent entities first)?
- [ ] Is the dependency chain complete back to root entities?

**MEDIUM Priority Issues (Good to Fix):**
- [ ] Are authentication flows correct (proper join/login usage)?
- [ ] Is required authorizationRole properly addressed?

**LOWER Priority Issues (Optional):**
- [ ] Does scenario represent realistic user workflow?
- [ ] Is function naming business-centric and clear?

### 3.3. Issue Resolution Actions

**Remove Scenarios If:**
1. References non-existent APIs in any capacity
2. Has missing dependencies that CANNOT be completed (required APIs don't exist)

**Rewrite Scenarios If:**

2. Has incorrect authentication flow sequences
3. Dependencies are in wrong order (dependent entities before independent entities)
4. Dependency purposes don't reference Prisma schema relationships
